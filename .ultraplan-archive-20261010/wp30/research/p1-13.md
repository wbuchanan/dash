Rule, all channels, round half up: f <= 1: `255-(255-c)*f`; f > 1: `c/f`. When a channel that was non-zero would round to 0, Stata instead divides by the smallest non-zero channel (navy*100 = navy/26 = #010304; maroon*120 = #030101; "0 0 1*10" = #000001; "2 200 255*150" = #016480; "5 9 200*11" = #010228). Of 23 probes near the clamp (rounds 3 and 4), 20 fit. UNCLEAR: the three that do not are all a channel of 26 divided by exactly 52 (navy*52, "26 71 111*52", "26 200 200*52" clamp), where other exact halves do not clamp ("13 50 60*26", "5 9 200*10", "2 4 6*4", "1 2 3*2", "1 200 200*2"); no float model tried separates them. `scripts/extract_scheme_truth.py:_apply_intensity` (:305) lacks the clamp (its docstring says *255 matched; it would give #000000).

Invalid multipliers are ignored silently (base colour, no note): `navy*abc`, `navy*-1`, `navy*1e400`, `navy*.`, `navy**.5`, `navy*.5*2` all draw #1a476f. `navy*+.5` and `navy*5e-1` draw #8da3b7.

### Unknown colours and forms dash accepts but twoway does not (new findings)

- Unknown name in an option: twoway notes it and draws **black**, not the scheme colour: `mcolor(bogus)` #000000 (s2color and stcolor), `lcolor(bogus)` stroke #000000, bar `fcolor(bogus)` #333333 (black at inten80), `title("T", color(bogus))` #000000. dash draws the scheme default (`test/test_options.py:284-299` pins this; its docstring says twoway "draws the default colour", which the SVG contradicts). dash.sthlp:663 ("the scheme's default drawn, as twoway does") and :2718 are wrong for colours.
- Names are case-sensitive in twoway (`Navy`, `BG`, `FOREGROUND`: note + black). dash lowercases (dash_render.py:5473) and draws `Navy` as navy silently; `test_options.py:244-248` pins case-insensitivity.
- `mcolor("255,0,128")`: twoway r(198). dash draws #ff0080.
- `"#F00"`, `#f00`, `"#ff00"`, `#GG0000`: twoway silently keeps the default colour (#1a476f, no note). dash draws `#f00` as red; the other two are noted.
- Unquoted 6-digit hex `#ff0000` works in twoway; `#FF0000` too (dash lowercases, fine).

## 4. Approach

Split into two sections; both edit `dash_render.py` only on the Python side (dash.ado and dash_parse.mata do not parse colours; quotes are stripped before Python).

### P1.13a Stata colour grammar (M)

1. `OptionTranslator.stata_colour(value, *, base=None, background=None, foreground=None) -> (hex, alpha)` as a static method (so it travels into the served app with the class source; no new module-level function, so `ServerAppBuilder._shared_stat_lines` is untouched). Raises `ValueError` on an unknown value. Grammar, from the measurements above:
   - Bound the input (e.g. 200 characters) before any parsing; plain splitting, no backtracking regex.
   - Split an opacity `%#` and a multiplier `*…` in either order. A multiplier that is not a finite number >= 0 is ignored silently (twoway).
   - Base: an exact-case name from `_COLOR_MAP`; `bg`/`background` and `fg`/`foreground` (lower case only) from the passed scheme colours; three integers 0-255; four numbers as CMYK (proportions when all <= 1, else integers 0-255); `hsv H S V`; `#rrggbb` (6 digits); an empty base (bare `*#`/`%#`) uses `base`. `none` with a multiplier is `0 0 0` (twoway draws `none*.5` #808080).
   - Intensity as measured, including the f > 1 clamp; output always `#[0-9a-f]{6}`.
   - `translate_mcolor` and `parse_color_alpha` delegate to it and keep their signatures (keyword-only `base`, `background`, `foreground` added), so the ~30 existing call sites keep working.
2. `SchemeParser`: add `foreground_color` (`color foreground`, default #000000); `_color`/`_color_alpha` resolve with this scheme's background/foreground (resolve those two first; guard `color background bg` self-reference); a present but unreadable value draws #000000 for every key, as twoway does (today `color background` falls to #d9e8f0, plotregion/legend to #ffffff, grid to #d9e8f0); bare `*#` in a scheme draws #ffffff (measured). Absent keys keep today's defaults.
3. `GlyphMapper`: one helper `_colour(value, option, base)` passing `self.scheme.background_color`/`foreground_color`; route `_apply_marker_opts`, `_apply_line_opts`, `_apply_fill_opts`, `_apply_mlabel_opts`, `_ci_band_style`, `_apply_colorvar` and the direct `translate_mcolor` sites in `map_bar`, `map_rbar`, `map_area`, `map_rarea`, `_histogram_quads`, `map_dropline`, `map_rcapsym`, `map_scatteri`, `map_pcarrow`, `map_pcbarrow` through it.
4. Graph level and text: `_dash_graph_color(option, raw)` and `_textbox_color(opts, default)` take the scheme colours (and a base, see b). The served app emits its own graph-level block as strings (dash_render.py:35226-35255) beside the saved one (:30340-30376); change both, or better, move both onto one shared function so the modes cannot drift.
5. `_resolve_kpi_color`: accept the same grammar before its CSS fallback (KPI is dash-only; its CSS leniency, including #fff, stays).
6. Apply decisions D1-D3 (section 7).
7. `scripts/extract_scheme_truth.py`: add the f > 1 clamp to `_apply_intensity` and CMYK/HSV to `ColorResolver.resolve_with_opacity`; regenerating the 20 shipped schemes must be a no-op (they hold hex).
8. Help: dash.sthlp colour paragraph (:2716-2719), the validation paragraph (:657-664), the user-scheme paragraph (:3499-3510); CHANGELOG "Results that change" for every look change (D1, D2).

### P1.13b Default colour with adjusted intensity, bare `*#` (M)

Each site passes its own pre-intensity default as `base`: markers p#mark, lines p#lineplot/p#line, fills p#bar/p#area, CI bands the ci/p#other style, marker labels, title/subtitle/note/caption/axis-title colours (`title color(*.5)` = heading*.5), graph region (`bg*.5`), plot region, KPI default. On filled layers the object's intensity then blends the rounded colour again (bar inten80, `fintensity()`); that needs intensity drawn as a blend, which is P1.2's D11 (today `_apply_fill_opts` :8844-8859 writes fintensity into `fill_alpha`, and `_blend_intensity` :8293 clamps f to [0,1]). Land after or with P1.2's D11.

Both modes: the mapper and translator are shared by source, so saved and served draw from one code path; colours are fixed at build, and a served recompute after a filter move rebuilds layers through the same mapper. Tests assert the colours before and after a move (`test/test_embedded_rows.py:_served_after_move`) and that the saved page's JS callbacks never write a colour.

## 8. Decisions for the maintainer

- D1. Unknown or out-of-range colour (`mcolor(bogus)`, `"300 0 0"`): (a) draw black with the note, as twoway does (flip `test_options.py:284-299`, fix dash.sthlp:663/:2718); (b) keep the scheme colour and document the difference. Implication of (a): a dashboard with a typo'd colour turns black. Recommend (a), in line with M1's "Match Stata".
- D2. Case of colour names (`Navy`, `RED`, `BG`): (a) case-sensitive as twoway (note, then D1's colour; flip `test_options.py:244-248`); (b) keep dash's lowercasing as a documented extension. Recommend (a); CHANGELOG line.
- D3. Forms twoway does not accept: `"255,0,128"` (twoway r(198)) and 3/4-digit or invalid hex (twoway keeps the default silently). (a) match: refuse the comma form (r(198) at the Stata gate, or a note under the open "Refuse vs note" decision) and treat short hex as unknown with a note; (b) keep as dash extensions. Recommend (a) for graph options, keeping CSS leniency in KPI cards.
- D4. P1.13b timing: wait for P1.2's D11 (intensity as a blend), or ship bare `*#` on filled layers over today's alpha approximation. Recommend waiting (same or later batch).
- Not a decision: the navy*52 boundary stays UNCLEAR and is documented.

### Corrections

1. **The intensity rule holds only under `system naturally_white 1`.** Under `naturally_white 0` (s1rcolor, or a user scheme that sets it), `*#` gives c*f for f < 1 and for f > 1.
   - s1rcolor: `navy*.5` #0D2438, `navy*1.5` #276BA7, `*.5` #808000 (p1 is yellow), `bg*.5` #000000, `fg*.5` #808080, `"hsv 240 1 1*.5"` #000080, `title(, color(*.5))` #808080.
   - `#include s2color` + `system naturally_white 0`: `navy*.5` #0D2438, `navy*1.5` #276BA7, `*.5` #0D2438, `bg*.5` #75797A, `fg*.5` #000000; a scheme line `color p1 navy*.5` gives #0D2438.
   - CMYK is not affected: `"0 0 0 128"` is #7F7F7F under both settings.
   - Nothing in dash reads `naturally_white`: there is no match in dash_render.py or in any dash-*.scheme. `scripts/extract_scheme_truth.py:_apply_intensity` (:304) ignores it too.
   - Needed: `stata_colour(...)` takes a `naturally_white` input, and `SchemeParser` reads `system naturally_white`, default 1, bounded to 0/1.
   - UNCLEAR: whether the clamp to the smallest non-zero channel applies under `naturally_white 0` (not measured).
2. **"P1.13a depends on nothing" is wrong.** P1.2 (p1-02.md §3 A/B/E) adds `system naturally_white` to the extractor, `_FALLBACK_PROPS` and SchemeParser, and extends `_blend_intensity(hexval, f, naturally_white)`. P1.13a needs that key. One intensity function must serve `fintensity()`, scheme intensity and `colour*#`. P1.2's c/f rule lacks the f > 1 clamp found here; fix it once, in the shared function.
3. **Step 2 ("a present but unreadable value draws #000000 for every key") is not true for every key.**
   - twoway does not read `color p#mark`. `color p1mark bogus` leaves markers #1A476F with no note, and `color p1mark red` also gives #1A476F. dash reads it: `color p1mark red` draws #ff0000. Land step 2 with or after P1.4 (h), which stops reading `p#mark`. Otherwise `color p1mark bogus` turns dash's markers black.
   - Step 2 is right for `color p1lineplot bogus` (twoway line #000000 with a note; dash falls back to p1's #1a476f) and `color p1bar bogus` (fill #333333 with a note; the outline stays #1A476F).
   - `color p1markfill bogus` gives a black fill and `color p1markline bogus` a black outline. dash reads neither key; that is P1.4 (h).
   - So step 2 reverses `SchemeParser._stub_color_alpha`'s deliberate chain fallback (its docstring says "rather than to black"). `_stub_color_alpha`, `_line_color` and `_band_color` are missing from §6.
4. **§7 "P1.21 (xline colours): new colour sites" is wrong.** P1.21 covers numlists, `lstyle`, `noextend` and `lalign`. xline/yline `lcolor()` is an existing site at HEAD:
   - `_dash_refline_draw` (dash_render.py:26327-26350) calls `translate_mcolor`, and it is copied into the served app by name (`_glyph_layer_lines` :33383).
   - twoway: `xline(3000, lcolor(navy*.5))` #8DA3B7; `yline(25, lcolor(bogus))` #000000 with a note (dash draws the scheme's xyline colour); `lcolor(red%50)` stroke-opacity 0.50; `lcolor(%50)` #C10534 (s2color's xyline) at 0.50.
   - Add this site to step 3, to the P1.13b base list (`scheme.xyline_color`) and to D1.
5. **The test plan's "the saved page's JS callbacks never write a colour" is wrong.**
   - The saved page's KPI JS rebuild writes `color`/`bgcolor`, resolved at build by `_resolve_kpi_color` (:31811-31814).
   - The served app resolves KPI colours again on every filter and selection callback: `_dash_kpi_card` (:34145) → `_dash_kpi_card_html` → `_resolve_kpi_color`.
   - Assert instead that the JS writes only build-resolved, sanitised values, and that served KPI colours are unchanged after a filter move and after a brush.
6. **Step 7 ("regenerating the 20 shipped schemes must be a no-op") is wrong** once `naturally_white` is transcribed: dash-s1rcolor.scheme gains `system naturally_white 0`.
7. **The flip list is incomplete.** Add `test/test_security_surface.py::TestAColourMustBeAColour::test_a_scheme_cannot_break_out_of_its_css_rule` (:195). It pins `body background-color: #d9e8f0` for an unreadable `color background`; step 2 makes that #000000. Keep its one-rule-per-line and hex-only assertions. (`test_scheme_review_fixes.py::TestMarkColourIsForMarkers` :384 is P1.4 (h)'s flip.)

### Gaps

- **`%#` opacity is dropped silently wherever `translate_mcolor` is called directly.** `translate_mcolor` strips the suffix (`translate_mcolor('red%50')` gives '#ff0000').
  - Sites: `_apply_mlabel_opts` :9451, `_textbox_color` :4848, `_dash_refline_draw` :26345, `_dash_graph_color` :15422, `map_bar`/`map_rbar` `color`/`bfcolor`/`blcolor`, `map_area`/`map_rarea` `color`, `_histogram_quads`, `map_dropline`, `map_rcapsym`, `map_scatteri`, `map_pcarrow`/`map_pcbarrow`, and `colormissing`.
  - twoway honours it: `mlabcolor(red%50)` text opacity 0.50, `title("T", color(red%50))` opacity 0.50, `xline(3000, lcolor(red%50))` stroke-opacity 0.50.
  - No DROPIN item names this. Keeping `translate_mcolor`'s signature, as the approach proposes, keeps the drop. See D5.
- **A bare `%#` at those sites draws opaque black with no note.** `translate_mcolor('%50')` and `translate_mcolor('')` return '#000000' through `_COLOR_MAP[""]` (:5224). So `title("T", color(%50))`, `xline(#, lcolor(%50))` and `bgcolor(%50)` are black. twoway draws the title #1E2D53 (heading) at 0.50 and the xline #C10534 at 0.50. The new grammar's "an empty base uses `base`" must remove the `""` key, or never reach it.
- **British spellings are dash-only.** `grey`, `dimgrey`, `bluishgrey` and `ltbluishgrey` (:5226-5231) are not Stata names. twoway `mcolor(grey)` gives a note and #000000 (measured); dash draws #808080 with no note. Add them to D3. A check of `_COLOR_MAP` against all 92 `color-*.style` files finds no Stata name missing.
- **Case in scheme files.** `color p1 Navy` and `color p2 RED` give black with six notes each in twoway (measured). dash draws #1a476f and #ff0000. D2 must say that it covers scheme files too, including third-party schemes.
- **D2 (a) changes KPI colours silently.** `color(Navy)` would fail the Stata grammar and fall through to the CSS branch (`navy` is in `_CSS_NAMED_COLORS`), so the card would draw CSS navy #000080, where it draws #1a476f today. Decide whether the KPI path keeps a case-insensitive Stata lookup ahead of CSS.
