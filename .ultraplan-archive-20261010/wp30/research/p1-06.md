## 5. Proposed approach (closes the item in both modes)

Fold in Stata, at registration, into the existing x keys. The spec never carries a t key, so dash_render.py, the saved page, the served app and filter moves are untouched. They already draw `xlabel`, `xtick`, `xline`, `xscale` and `xtitle` on date axes in every unit (test_served_dates.py `TestANumberOnADateAxisIsAStataDate`). GitNexus rates the renderer readers this relies on CRITICAL (`_dash_parse_axis_spec`, 8 impacted) and HIGH (`_dash_date_axis_spec`, 5). That is a further reason not to edit them.

### 5.1 Declare (dash.ado)

1. Add twoway's spellings to both syntax blocks: `_dash_parse_graph_opts` (dash.ado:714-736) and `_dash_parse_plot_opts` (dash.ado:924-985).
   - `TLabel(string asis) TTICk(string asis) TMLabel(string asis) TMTick(string asis) TSCale(string asis) TTitle(string asis) TLIne(string asis)`. The capitals give twoway's measured minimums: tl, ttic, tml, tmt, tsc, tt, tli.
   - Check with -syntax- that `t()` still reaches T1title, `tm()` and `ts()` still fall to the catch-all, and `tti()` reads as ttitle.
   - Plurals (`tlabels`, `tlines`, `tticks`) are renamed by `_dash_route_axis2` once the family table accepts the side letter t (step 3).
   - Axis-2 forms: `TLABEL2 TTICK2 TLINE2 TSCALE2 TTITLE2 (string asis)`, mirroring `XLABEL2` and the others.
2. Add the 12 keys to both sreturn blocks, to the seven `foreach gk/gkey in` lists (dash.ado:4274, 5066, 5100, 5200, 5272, 5304, 5602; guarded by test_abbreviations.py `test_the_seven_graph_key_lists_agree`), and to dash.ado:237 `_needed` for any new Mata function.
3. Add pending lines for tmlabel and tmtick in the `_dash_pending` blocks (dash.ado:786-815 graph, :1054 plot). They fold and store, and are named until P2.2 draws minor ticks.

### 5.2 Merge categories (dash_parse.mata)

- `_dash_rep_cat` (dash_parse.mata:4664): tlabel, ttick, tmlabel, tmtick and their 2-forms are "L"; ttitle(2) is "T"; tline(2) is "X".
- tscale(2) gets a new category "D". It keeps every `range()` word, because "S" unions only numeric ranges: `_dash_rep_subs` at dash_parse.mata:5662-5710 drops all but the last range() when one is not a number, which would lose `tscale(range(1999m1)) tscale(range(2006m1))`. The fold converts and unions afterwards.

### 5.3 Axis machinery (dash_parse.mata)

- Let `_dash_ax_parse` (dash_parse.mata:5391) accept the side letter `t`. It already returns twoway's plural name for messages ("tlabels", "tlines").
- `_dash_route_axis2` (:5486): for t, axis 2 is written as `t<fam>2` and axis 1 drops the word.
- `_dash_axreq_add` (:5560): side code 1 = x, 2 = t, 3 = y, so `_dash_axreq_check` orders X, T, Y as f12/f13 measured. It reads t rows against the x axes (`xset`) and names them "tlabels(...) not allowed, xaxis3 does not exist".
- Update test_abbreviations.py's `_dash_axfam` assertions only if the table itself changes. Keeping the side letter outside the table avoids that.

### 5.4 The fold (new ado program `_dash_taxis_fold` with Mata helpers)

**Where.** In `_dash_plot`, after the after-comma merge loop and the axis check (dash.ado:~5280-5296), and before "Validate the graph-level values (WP-15)".

**Per-segment inputs.** Add a c_local `_seg_xvar_out` in `_dash_process_segment`. It is the variable the x axis is formatted by:
- xvar for yx types;
- `var` for histogram and kdensity;
- x1 for pc types (pin with a probe where x1 is %tm and x2 is %td);
- "" for function, scatteri, pci and pcarrowi.

Keep `_seg_xaxis_out` and the type for each segment.

**Base format for x axis a ∈ {1, 2}.** Take the first segment on axis a. If its type is in {lfit qfit lfitci qfitci lpoly lpolyci kdensity function scatteri pci pcarrowi}, the base is "numeric" (the m6.do table). Otherwise it is `: format xvar`. Read at registration; twoway reads it at draw time, which is the same in practice.

**Format state per axis.** Track the four tickset formats {major, minor, majornl, minornl}:
- initialise all four to the base;
- the last `format()` in the merged g_xlabel, g_xmlabel, g_xtick and g_xmtick (axis-matched) overrides its tickset.

**Process T keys in twoway's family order:** scale, label, mlabel, tick, mtick, title, line.

- **Label and tick family** (tlabel → major, tmlabel → minor, ttick → majornl, tmtick → minornl):
  - Unit = `_date2elapsed`'s rule on that tickset's format (accepts `%-t`).
  - Port twoway's grammar: Rules (`#N`, `##N`, `minmax`, `none`, `.`), then NumTextList with datesok. That covers single positions, optionally parenthesised; `a(d)b` rules with date or number ends anywhere; and quoted labels after single positions only (e10).
  - Convert each literal. Write rules as `A(d)B` with converted ends; dash's `_dash_parse_axis_spec` expands them.
  - After the positions, apply the option's own `format()` to its tickset (k03, k04).
- **Line family** (tline): unit = `get_time_format` (the first tickset format whose two-character prefix is `%t` or `%d`; `%-t` is non-date, g02).
  - Expand rules with Stata's own `numlist` after converting the ends. This gives r(123) "invalid numlist has too many elements" at twoway's limit (m8), and avoids P1.21 because the result is explicit numbers.
- **Scale** (tscale): the `range()` words use the `get_time_format` unit; union them; write `range(lo hi)`. Other sub-options pass through.
- **Title** (ttitle): no conversion.

**Converting one token** (Mata, values read with `st_local`, never macro-expanded):
1. Stage 1, as `_confirm_number_or_date`: a number, `.`, `.a`-`.z`, or valid for any of d, w, m, q, h. Otherwise the family's "invalid label specifier" or "invalid line argument" message.
2. Stage 2, as `_date2elapsed`'s `Evaluate`: if the axis unit is set, evaluate `unit(tok)` via `_stata("scalar <tempname> = " + unit + "(" + tok + ")", 1)`. An integer result replaces the token. Otherwise the token must be a number, or the twoway message (ticklist, argument or range) is raised with its rc (198 or 121).
3. Security: a gate runs before any evaluation. A token holding a backtick, `$`, `"`, `'`, `\`, a bracket, a brace, whitespace or a control character is never evaluated, and is refused as "not a date". All messages go through `_dash_say` (user text shown as typed). Cap the token count, using the existing `$dash_max_*` limit style, so a pathological list cannot run thousands of `_stata` calls.

**Merging into x.** `g_x<fam>[2] = _dash_rep_merge(x key, g_x…, converted)`. The T copy comes after X, as measured (c14/c15/c35; c36 for lines). Then clear the g_t* keys so the spec never carries them.

### C1. Error: "no renderer change is needed" is false on a mixed x axis (both modes)

The fold takes its unit from twoway's first plot. dash's renderer draws a date axis only when every layer on it has a date variable of one kind (`_dash_figure_date_kind`, dash_render.py:788-818). Otherwise it draws a LinearAxis and keeps the date layers in epoch ms (P1.23 sub-claim 4, still TRUE for raw layers).

mixed.py takes the folded keys `xline 504, xlabel 480(12)528` and renders three layer sets, each identically in the saved page and the served app:

| layers | result |
|---|---|
| `tsline y` on %tm | DatetimeAxis; Span 2002-01-01; correct |
| `(tsline y t) (line z n)`, n unformatted | LinearAxis. The tsline x runs 2000-01-01..2004-12-01 in ms, while the Span and ticks sit at 504 and 480..528, about 1e12 away. |
| `(tsline y t) (line z d)`, %tm and %td | The same LinearAxis failure |

### C3. Security: use Mata's string date functions instead of `_stata()`

The proposed `_stata("scalar t = " + unit + "(" + tok + ")")` builds Stata command text from user input. Its blacklist gate does not name `(`, `)`, `,` or `;`. "A bracket" is ambiguous, and a `)` in a token would end the pseudo-function and let the rest run as an expression.

Mata has functions that take the token as a plain string value, with no expression evaluation:

| unit | function |
|---|---|
| d | `date(tok,"DMY")` |
| w | `weekly(tok,"YW")` |
| m | `monthly(tok,"YM")` |
| q | `quarterly(tok,"YQ")` |
| h | `halfyearly(tok,"YH")` |
| y | `yearly(tok,"Y")` |

They return the same value as the pseudo-function for all 78 tokens probed (k1.do, k2.do, k3.do; `XPAR_TOTAL n=33 differ=0` for k3). They also return missing in exactly the cases where the pseudo-function is r(198). The probes cover:
- every lenient form in 3.5 (2000x1, 2000+1, 2000M1, 1+jan+2000, 1january2000, 1.1.2000, 2000.m1);
- every rejected form in 3.5 (2000m13, 99m1, 10000m1, 2000-01-01, 2000w53, 2001q5, 2002h3, y(2001.0), 1e3);
- the range ends 1000m1 and 9999m12.

This removes the evaluation path and the per-token `_stata` cost. The 3.5 claim "it must call Stata's own pseudo-functions" is therefore wrong. The gate remains useful only as input validation, written as a whitelist. TA-09 should assert that no `_stata`/`stata()` call takes user text.
