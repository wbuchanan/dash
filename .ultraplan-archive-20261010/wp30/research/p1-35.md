This is how an older Stata answers a `version` it does not know. By analogy (UNCLEAR, not run), Stata 15.1 answers `dash` with Stata's own r(9) message, not dash's.


**Conclusion:** under 19.5, `version 16` keeps every newer twoway feature: stc colours, colorvar(), the stcolor scheme, rpcap, and stcolor as the default scheme. The static evidence in section 3 shows Stata 16 and 17 have none of these. So twoway truth for Stata 16-18 can be measured only with the older binaries, never by version control in 19.5.

## 3. Static evidence from the installed older Statas (read-only file reads; nothing run)

The installed versions are 14.2.427, 15.1.640, 16.1.884, 17.0.132, 18.0.141, 18.5.030 (`/Applications/Stata`) and StataNow 19.5.056 (Info.plist CFBundleShortVersionString). Binaries (`lipo -archs`): 14 and 15 are x86_64 only; 16.1 through 19.5 are universal (x86_64 arm64).

### 3.1 What dash calls exists in Stata 16 (heuristic scans)
- **Mata.** The external functions dash_parse.mata calls were checked against `ado/base/m/mf_*.sthlp`. None is documented in 19.5 but missing from 16.
- **Stata functions.** Functions in dash.ado and dash_setup.ado were checked against `ado/base/f/f_*.sthlp`. Only `regexr` and `regexs` appear "new", and that is a false positive: they are older than 16 and only their help file was split later.
- **Stata commands.** Statement-leading command words were checked against 16's help and ado files. None is new.
- **c() values.** Every `c()` value dash reads, including python_exec and userversion, is in 16's creturn.sthlp.
- **twoway function.** `twoway__function_gen.ado` is byte-identical in 16 and 19.5 (v1.2.0 28jan2015). `global_g.class` has `callerver` in both (used at dash.ado:5996-6007).
- **sfi.** Every sfi member dash uses is in 16's `ado/base/py/sfi.py`: Macro.get/setLocal, getGlobal, setGlobal, Data.get*, isVarTypeStrL, ValueLabel.getValueLabels/getVarValueLabel, StrLConnector.isBinary, SFIToolkit.displayln/stata/pollstd. The one exception is in 3.3.

### 3.2 twoway truth that differs by version (what dash would have to match)
| Feature | 16.1 | 17.0 | 18.0 | 18.5 | 19.5 | dash today |
|---|---|---|---|---|---|---|
| stcolor-family schemes (13 files, scheme-st*.scheme) | no | no | yes | yes | yes | ships dash-st*.scheme, draws them on any Stata |
| default c(scheme) | s2color (UNCLEAR, by doc) | s2color (UNCLEAR) | stcolor | stcolor | stcolor | follows c(scheme) (dash.ado:6765, 8002), so correct by construction |
| colours stc1-stc15, stblue/stred/stgreen/styellow (color-*.style) | no | no | yes | yes | yes | accepted (dash_render.py:5176) |
| colorvar() (colorvar_*.sthlp) | no | no | yes | yes | yes | drawn; help says "Stata 18's own" (dash.sthlp:3115) |
| by() legend_cols/rows from the scheme (bygraphstyle-default.style) | no | no | yes | yes | yes | not read by dash |
| twoway rpcap, rpspike, rbspike, rtable, y3xview (twoway_*_parse.class: 59 files in 16-18.5, 65 in 19.5) | no | no | no | no | yes | rpcap/rpspike refused with "Use Stata's own twoway X" (dash.ado:3496-3512) |

- **Classic schemes.** s1color, s2mono, s2manual, s1mono and economist are identical in 16 and 19.5. s2color only adds keys from 16 to 19.5 (bar labels, forest plot); the one line removed is its version header. sj changes only its label. So scheme truth for classic schemes should carry over to older versions.
- **Style files.** 41 style files are new in 19.5 and none were removed. Three changed: anglestyle-ninety (a comment), bygraphstyle-default (legend cols/rows), and seriesstyle-p#bar (its label).

### 3.3 A version-dependent defect WP-29 added
`class BreakError` is absent from sfi.py in 16, 17 and 18.0, and present in 18.5 and 19.5. `pollstd` is present in all five. `_dash_stata_poller` (dash_render.py:37114-37133) returns `(None, ())` when BreakError is missing. So on Stata 16-18.0 the launcher never polls, and Break in GUI Stata cannot stop `dash serve`. That contradicts dash.sthlp:1563 ("Break -- the Break button or menu item ... stops it at once"). This is static evidence only; behaviour on those versions was not run.

### 3.4 A version-dependent message
dash.ado:3496-3512 tells the user to "Use Stata's own twoway rpcap|rpspike". None of those types exists before 19.5 (they are absent from 18.0's and 18.5's ado/base/t), so the advice is wrong on any older Stata. test_parser.cscript P1A-59 (:553-580) pins the text.

## 5. Approach (split in two)

### P1.35a: declare and enforce one Stata floor (any floor value; S-M)
1. **Name the floor once.**
   - Add `_dash_statamin` (rclass, returns `r(statamin)`) next to `_dash_pymin` in dash_setup.ado:489.
   - dash.ado carries the same constant in a new `_dash_require_stata`, which follows the pattern of `_dash_python_ok` and `_dash_require_python` (dash.ado:189-215): a pure function `_dash_stata_ok "<version>" "<min>"` -> r(ok), so a cscript can reach the refusal state on 19.5.
   - The guard program declares `version 13` or nothing, never 16, so an older Stata runs it and prints dash's words. The proposed text: "dash requires Stata N or later; this is Stata 15.1". It exits 9, Stata's own code for a version refusal.
2. **Call the guard first.** `dash` (dash.ado:84) and `dash_setup` (dash_setup.ado:19) call it as their first statement, before `version 16.0`. dash_setup also prints a summary line, "Stata ......... OK (19.5)", or adds a FAILURE line through its accumulator.
3. **Keep the `version 16.0` lines.** They fix the language level that every test ran under, and they are not a statement of the minimum. BUGS.md:568 and :1287 show that this level changes behaviour inside dash. Raising them to 19 changes semantics in 91 programs for no user benefit; if the maintainer wants it anyway, it needs a full cert and pytest pass. A pytest guard pins that every program's first statement is `version 16.0`, so the guard and the version line cannot drift apart.
4. **State the floor.**
   - dash.pkg: `d Requires: Stata N or later; Python 3.13+, ...`. Coordinate with P2.29, which owns Author and KW.
   - dash.sthlp:3780 Dependencies: `{ul:Stata N or later}`, tested on StataNow 19.5, macOS arm64.
   - dash_setup.sthlp:123.
   - CHANGELOG.md "### Requirements" (:607).
   - ROADMAP.
5. **Make the rpcap/rpspike advice depend on the version** (only if N < 19.5). Move the advice into a Mata helper `_dash_undrawn_advice(type, has_twoway_type)`. dash.ado decides `has` with `capture findfile twoway_<type>_parse.class`.
6. **Document Break below 18.5.** In dash.sthlp's Blocking behaviour paragraph, say that Break in GUI Stata needs Stata 18.5 or later (sfi.BreakError), or give the fallback chosen in P1.35b. Only needed if N < 18.5.

Both modes: the guard runs before either the saved page or the served app is built. The served child is Python, not Stata, so after a filter move nothing depends on the Stata version except the launcher's Break polling (step 6).

### P1.35b: certify the older versions (only if the floor chosen is below 19.5; L-XL)
1. **Runners.**
   - scripts/stata_slot.sh: take `STATA` and `STATA_ARCH`, keeping today's defaults.
   - run_cert_suite.sh: take `STATA_ARCH`.
   - Makefile: add `cert-matrix STATA_MATRIX="..."`, giving one verdict and one log per version.
   - These overlap P1.34.
2. **Truth per version.**
   - Run every `scripts/extract_*.do` under each version into scratch.
   - A new `scripts/diff_truth_versions.py` diffs the output against the committed fixtures.
   - Each fixture's `_meta` gains `stata_versions_verified`. Where a truth differs, the fixture keys it by version, and the pytest readers pick the running version's entry.
   - This needs P3.7's missing generators. 14 fixtures (e.g. kpi_truth, geometry, natscale) cannot be regenerated today.
3. **Cert pins.** Branch on `c(stata_version)` and assert each version's own truth. Never skip, because a skip is not a pass (cert_verdict.py). Cases to branch: colorvar, stcolor and stc colours, P1A-59, and by() legends.
4. **Fixes.** Fix what the matrix finds. Predicted from section 3:
   - Break below 18.5.
   - The rpcap/rpspike advice.
   - dash drawing colorvar, stc colours and stcolor schemes where twoway 16/17 refuses them. Whether dash refuses or notes these is the §4 "Refuse vs note" decision.
   - The Python 3.13 load under 16 and 17 (unknown).

## 9. Decisions only the maintainer can make
1. **The declared Stata floor.**
   - (a) **19.5 (StataNow).** The only version measured, which follows DISCOVERY Q8's rule that "the floor is what is tested" (test_version_floor.py docstring). Honest and cheap. It excludes every Stata 16-19.0 user, and Stata 19.0 (non-Now) is not installed, so whether 19.0 has rpcap/rpspike is UNCLEAR.
   - (b) **18.0 after measuring 18.0 and 18.5.** Covers the stcolor era, where colorvar and stc colours exist, so few twoway truths differ. Break below 18.5 still needs a fallback or a note.
   - (c) **16 after measuring 16.1, 17, 18.0 and 18.5.** Keeps today's implied promise and has the widest reach. It needs per-version truths for colorvar, stcolor and the new types, and the Python 3.13 load under 16 and 17 is unknown.
   - **Recommendation:** run P1.35a now with N = 19.5. Authorise P1.35b, then lower N to the oldest version whose matrix run is green. Static evidence (section 3.1) suggests 16 or 18 is reachable.
2. **Allow the older console binaries (CLAUDE.md rule 10), and set python_exec for 17 and 18 once, permanently.** Recommendation: allow the console binaries only, through stata_slot.sh, with the GUI ban kept.
3. **Raise the `version 16.0` lines or keep them.** Recommendation: keep them as the tested language level and enforce the floor with the explicit guard.
4. **On Stata 16/17, refuse or note what twoway refuses there** (colorvar, stc colours, stcolor schemes), or keep drawing them as dash extensions. This joins §4 "Refuse vs note". Recommendation: keep drawing them, and name the version in the help.
5. **BE and SE.** They cannot be measured here. Recommendation: say "measured on MP only".

### A. The floor is already decided: M2 supersedes sections 5 (P1.35b), 9.1, 9.2 and 9.4
`.ultraplan/wp30/decisions.md` (recorded 03oct2026 and binding on every section) has M2 for P1.35: "Raise floor to 19". Its binding reading is: "dash declares version 19 and refuses an older Stata with a clear message. Only /usr/local/bin/stata-mp (StataNow 19.5) is run; the Stata 14-18.5 binaries on this Mac are never run." The note presents the floor as open and never cites M2. The plan must read it this way:
- **P1.35b is out of scope.** No version matrix, no change to rule 10, no `python_exec` rc edits for 17 or 18 (that would also be a persistent configuration change), and no per-version truths. Decisions 9.1, 9.2 and 9.4 are answered or moot. 9.5 (BE/SE wording) remains.
- **N = 19, not 19.5.** The guard accepts `c(stata_version) >= 19`, so Stata 19.0 (non-Now) is admitted but never measured. The help says "Stata 19 or later; tested on StataNow 19.5 (MP), macOS arm64".
- **Section 5 step 3 ("keep the `version 16.0` lines") contradicts M2's "dash declares version 19".** It also contradicts every sibling note: p1-25.md:151, p1-27.md:283, p1-28.md:193 and p1-32.md:189/194 all expect P1.35 to rewrite `version 16.0` to 19 in every program. The plan should take the sweep. All 91 lines, 79 in dash.ado and 12 in dash_setup.ado, become `version 19`, not `19.5`. The guard admits 19.0, and 19.0 would then fail a `version 19.5` line with Stata's own r(9). The guard constant and the version level must be one number.
- **Steps 5 and 6 are moot, and the note's UNCLEAR about 19.0 is resolved.** StataNow's `ado/base/w/whatsnew18to19.sthlp:906-919` and `:1863-1876` list `twoway rpcap` and `rpspike` as Stata 19 release highlights, without the "(StataNow)" mark. So 19.0 has them, and the advice at dash.ado:3496-3512 is right on every admitted version. `sfi.BreakError` is in 18.5's sfi.py (re-verified: 16, 17 and 18.0 have none; 18.5 and 19.5 have it), so 19.0 has it, and dash.sthlp's Break claim holds at the floor. Only the comment at dash.ado:3496 ("twoway plot types in StataNow 19.5") should say Stata 19.

### B. The sweep to `version 19` was measured (smoke test, not a certification)

The plan should list which paths reach it with the global empty (it is dropped at dash.ado:5363), and pin that function-layer points do not change.

### D. Guard placement verified
- dash.ado and dash_setup.ado contain only one-line `python:` statements and no `python:`…`end` blocks. So Stata 16-18 loads both ado files whole, and the guard is reachable. A Python block's `end` would close the program early on a Stata without Python.
- dash.ado's top-level `capture run dash_parse.mata` (:81) runs before any program, and it is captured.
- The guard must be the first statement of `dash`: before `version` (:85) and before `_dash_require_mata` (:92). It must also be the first statement of `dash_setup` (:19-20).
- **Order across items:** the Stata guard, then the Mata guard, then P1.32's Python/dependency guard, then P1.27's prefix strip and P1.28's `rclass` dispatcher. All four items edit dash.ado:84-145.
- **Both modes are covered.** The saved page and every served route (`dash serve`, `dash build, server`) start from `dash`, and an app started by hand is Python only. The served child is launched with `sys.executable` (dash_render.py:37318). Its value under Stata 16-18's embedding is unmeasured, but M2 makes that moot.
