## 3. Truths this item must match (measured, StataNow 19.5)

- **SystemExit is rc 0 under Stata's `python:`** (m3.do), so a guard must never raise SystemExit in Stata's process. This rules out GAPS2 H6 plan step 1 as written. WP-29's M4b says the same (dash_render.py:1866).
  ```
  capture noisily python: raise SystemExit("dash: numpy is not installed …")  -> "SystemExit: dash: …"  RC3=0
  capture noisily python: raise SystemExit(1)                                 -> RC4=0
  capture noisily python: raise ImportError("dash: … run dash_setup")         -> traceback, RC5=7102
  ```
- **Stata accepts Python 2.7 and later** (Stata P manual, docs/p.pdf: "Stata supports both of them starting from Python 2.7"), so a 2.7 to 3.6 link is reachable. The Python 2.7 binary on this Mac is i386 ("Bad CPU type"). It is UNCLEAR at run time, but the proposed probe line is valid Python 2 syntax and runs on 3.3.5 and 3.6.6.
- **`python query` reads the version without initializing Python** (m7.do): `r(initialized)=0`, `r(version)="3.13.9"`, `r(libpath)=".../libpython3.13.dylib"`. It could serve for reporting. The guard instead reads `sys.version_info` from the running interpreter.
- **Probe cost** (m3.do, m8.do):
  - the version and find_spec probe as the session's first Python call: 0.158-0.178 s, Python start-up included;
  - a repeat call: 0.00 s;
  - `importlib.metadata.version` for three packages: 0.105 s;
  - the real `import numpy, pandas, bokeh.models`: 3.21 s.
- **`importlib.util.find_spec(m)` returns None when `sys.modules[m] is None`.** So the probe must test `sys.modules.get(m) is None and find_spec(m) is None`. Testing `m not in sys.modules` reads a blocked package as present, as measured.
- `c(machine_type)` = "Mac (Apple Silicon)". What the x86_64 slice reports is UNCLEAR: the project rule forbids running it.
- twoway itself has no Python dependency. There is no twoway truth fixture for this item, the same as WP-29 S09.

**Prototype (m8.do, a scratch program, not in the repo).** It reads the version and the missing packages as VALUES and refuses r(198):

## 4. Approach (closes H6a-d; saved page, `dash build, server`, `dash serve`, and the app run by hand)

A filter move imports nothing: the saved page is JS, and the served app imports at process start. So "before and after a move" is N/A. Each route is covered at its first Python use.

### 4.1 dash.ado: Stata-side guard (H6a, H6b, H6d)
- **New program `_dash_require_deps`.**
  - It calls `_dash_require_python` first. That keeps test_private_files.py `test_each_python_program_calls_dash_require_python_first` true.
  - Line 1 must parse on Python 2.7 and later: `python: import sys; from sfi import Macro as _dash_M; _dash_M.setLocal("_dd_v", "%d.%d.%d" % tuple(sys.version_info[:3]))`.
  - A Stata-side compare (a pure `_dash_pyver_below "<v>" "<floor>"`, testable like `_dash_python_ok`) refuses r(198) when the version is below the floor. The message names the version, `c(python_exec)`, the floor, `help python` and `dash_setup`.
  - Line 2 (3.4+ API, reached only above the floor): `… setLocal("_dd_miss", " ".join(m for m in ("numpy","pandas","bokeh") if sys.modules.get(m) is None and importlib.util.find_spec(m) is None))`. A non-empty list refuses r(198), naming the packages, `c(python_exec)` and dash_setup.
  - The decision is made from VALUES, never from an rc. That follows the hygiene rule in test_cscript_hygiene.py.
  - User and config text (the path) is echoed through `_dash_say`, per the WP-20 rule (TestUserTextIsEchoedAsText).
  - No global cache is needed: a repeat call costs about 0 s, and `cscript` drops globals anyway.
- **Call sites.**
  - The top of `_dash_xm_load` (dash.ado:4576), after `_dash_require_python`. Every in-process route reaches it first: `_dash_write_data`, `_dash_tmp_open`, `_dash_render_immediate`:6777 and `_dash_prepare_spec`:8057.
  - `_dash_do_render` (:413) as a second line of defence, for the render stand-in that tests use.
  - Not in `_dash_require_python` itself. That would make `dash clear` with no dash* folder run Python (A15) and would break ENV-17..19's "stops before Python runs".
- **The floor.** Replace the hard-coded "Python 3.13+" at dash.ado:212 with the same constant. dash.ado cannot rely on dash_setup.ado's `_dash_pymin` being loaded, so the floor is written once per file and pinned equal by a pytest (see 4.5). P1.33 sets the number (M3).

## 6. Maintainer decision

**D1. Package versions at render time: refuse, note or ignore?** (Shared with P1.30's D2.)
- (a) P1.32 refuses only a missing package and a Python below the floor; a below-minimum or out-of-window bokeh, numpy or pandas is a note (P1.30).
- (b) Also refuse below dash_setup's minimums (bokeh 3.8, numpy 2.3, pandas 2.3), at about +0.1 s per session (measured).
- (c) Ignore versions.

Implications: (b) can block users whose older packages render fine today. That is the same complaint P1.33 makes about Python.

Recommendation: (a). It is consistent with M3's "measure, then lower" stance, and the message still shows an old bokeh's ImportError text.

No other decision is needed. r(198) follows `_dash_require_python`'s precedent (ENV-06). The Python floor itself is M3/P1.33's.

## 7. Effort, risk, split, feasibility

- **Effort: M** (DROPIN says S). There are four code sites (dash.ado guard, renderer import block, app header, dash_setup:92), two help files, and about 6 pytest classes and 12 cscript cases.
- **Risk: yellow.** The guard becomes the first Python call of every dash command. `_generate_app_source` is HIGH in GitNexus. The changes are additive and the healthy path is unchanged: the probe costs 0.00 s after the first call.
- **Split**: not needed. If a batch needs room, split it as P1.32a (dash.ado, renderer and app guards: H6a, H6b, H6d) and P1.32b (dash_setup:92 retry and summary: H6c). Best batched as {P1.33, P1.32, P1.30}, in that order.
- **Feasibility here: high.** Every route is measurable on this Mac by in-process injection (meta_path or `sys.modules[m]=None`, `sys.version_info` patch, a `sfi` stand-in, a PYTHONPATH stub for the child). Real Pythons 3.6 to 3.12 exist for shell-level tests.
- **Not measurable here**:
  - Python 2.7 is i386 only;
  - an x86_64-slice Stata with an arm64 Python (the architecture-hint scenario) is forbidden by the project rule;
  - a real Stata linked to an old Python would need `set python_exec`, which was avoided to protect `~/.stata19/console/stata19.rc`;
  - Windows and Linux.

1. **An old bokeh is not caught by the guarded import block.** §4.2 and §6 claim that guarding :82-118 keeps an old bokeh's "cannot import name 'CustomJSTicker'" visible. It does not, because `CustomJSTicker` is imported only lazily (dash_render.py:22902, :23359 in `_dash_count_axes`, :23585).

2. **The served app also imports after start.** §4 says "the served app imports at process start". In fact the app's copied helpers keep lazy `from bokeh.models import …` lines (generated app m4.py:8803, :9420, :10035), and they run in each session's `modify_document`.

   - The keyed session URL answered **HTTP 500**. The ImportError (frames through bokeh `function.py modify_document`) appeared only in the child's stderr.

3. **D1(a) contradicts P1.30.** P1.30's own D2 recommendation (p1-30.md:184) is "(c) refuse below the floor", but this note's D1(a) makes a below-minimum bokeh only a note. The two notes must agree.

   - Add ENV cases for a blocked transitive dependency (jinja2) and a blocked extension module.
2. **dash.ado still does not check that Python can start** (the first half of the GAPS2 H6 title). Line 1 of `_dash_require_deps` is uncaptured, so a linked Python that cannot initialize still gives Stata's raw error.
