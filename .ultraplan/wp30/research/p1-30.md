## 6. Decisions for the maintainer

- **D1: ceiling policy** (DROPIN §4 "choose a bokeh ceiling policy").
  - (a) An exclusive ceiling at the first unverified minor, `bokeh>=3.8,<3.10`, raised only after a re-verification.
  - (b) A major ceiling, `<4`, as WP-29's regex comment anticipated. It admits 3.10.x, which is unverified today.
  - (c) No pip ceiling: a run-time note only.
  - Implications: (a) is the only option where "verified" is true, but dash_setup installs a bokeh one minor behind PyPI until each re-verification. (b) and (c) install 3.10.0 today (measured).
  - **Recommend (a).** Verify 3.10 inside this item if the bokeh 3.10.0 download is approved; the ceiling then becomes `<3.11`.
- **D2: run time outside the window.**
  - (a) Note and continue, in both modes.
  - (b) Refuse r(198) unless a global (e.g. `$dash_bokeh_unverified 1`) allows it.
  - (c) Refuse only below the floor.
  - **Recommend (a) above the window and (c) below it.** The floor is already a refusal in dash_setup, and 3.6-3.7 render today with no word. Refusing above the window would break users who need a newer Bokeh for other work. The internals guards (4c) carry the hard security line.
- **D3: granularity.** Exact patch versions (today's `VERIFIED_BOKEH`) or major.minor. PyPI already has 3.8.1, 3.8.2, 3.9.1 and 3.9.2. **Recommend major.minor**, matching conftest's `_mm`.
- **D4: dash_setup verdict for "above".** Warning (rc 0) or failure (r(198)). **Recommend warning**, with the pip line printed and nothing downgraded.
- **D5: lock, matrix, dev requirements and hash pinning** (K5 steps 1-3, OQ7). **Recommend:**
  - a `constraints` file is unnecessary once the ceiling sits in the spec.
  - a `requirements-dev.txt` (pytest, pytest-xdist, packaging) is cheap: put it in P1.30b.
  - a nox matrix belongs with P1.33/P1.34.
  - no hash pinning: numpy and pandas ship per-platform wheels, and the hashes would need refreshing on every release.

### C1. 4c's template guard, as written, would stop every served session (error)
"Render it once on an empty context" raises `jinja2.exceptions.UndefinedError: 'macros' is undefined` on the real template, under 3.8.0 and 3.9.0 alike (t2.py; `{% from macros import embed %}` in Bokeh's file.html, line 17). Use these instead:
- **Guard (runtime):** `"preamble" in bokeh.core.templates.FILE.blocks`. Both verified Bokehs list it among 12 blocks. If it is missing, raise the named RuntimeError.
- **Behavioural check** (a test, or once at launch, never per session):
  - `bokeh.embed.file_html(fig, CDN, "t", template=_dash_served_template())` must hold exactly one `http-equiv="Content-Security-Policy"`. Measured: 1 on both.
  - Confirmed independently: a parent with no `preamble` block renders `<html><head></head><body></body></html>` with no CSP, and raises nothing (t1.py).

### C2. 4c's origin guard needs a behavioural probe of `check_allowlist` (gap)
`_dash_harden_origin_check` (dash_render.py:3893) probes `match_host` only. It cannot see a Bokeh whose `check_allowlist` stops calling `match_host`. In that case it returns False, replaces nothing, and the lenient check stays: this fails OPEN.

Simulated in t3.py by swapping `check_allowlist` for a prefix matcher: harden returned False, and the probe origin was still admitted. The guard must therefore assert after hardening that `bokeh.server.util.check_allowlist("localhost.dash-origin-check.invalid:1", ["localhost:1"])` is False, and refuse to start otherwise. Measured:
- 3.8.0: True before hardening, False after.
- 3.9.0: False before and after.

### C3. AuthProvider drift can fail open too (gap)
4c covers only import failures. Gate A (`_dash_token_auth`, :4083) works by overriding the `get_user_async`/`get_login_url` properties. If a Bokeh renamed or stopped consulting that hook, the override would be silently ignored, and Gate A would admit every request. Only Gate B (`doc.session_context.request.arguments`, itself an internal) would remain.
- Today both verified Bokehs define `get_user`, `get_user_async`, `get_login_url`, `login_url` and `endpoints` (t3.py).
- Add a launch-time `hasattr` check, and keep the P0.12a "request without the key gets 403" tests in both baselines' runs (`make test` runs `DASH_BASELINE=stata` and `dev`, Makefile:36/40).
- List `_dash_session_token_ok`'s `session_context.request.arguments` in `_DASH_BOKEH_INTERNALS`.

### C4. `dash serve` would print the version note twice (approach gap)
`dash serve` runs `main()` in Stata's Python (dash.ado:8473 → dash_render.py:37628), so the note fires there. It then starts the child app with `_dash_launch_app` (:37672). The child's launcher prints the note too, and `_drain_stdout` (:37363) forwards every stdout line to Stata.
- Skip the launcher print when the parent already noted it: an env flag on the child, or a `--quiet-version` argument.
- Alternatively, skip `main()`'s note when `launch=True`.
- Test: exactly one note line in a `dash serve` log.

### C5. The venv route would downgrade a user's bokeh (missing decision D6)
`validate_venv_path` (dash_setup_lib.py:312) accepts any existing directory with a `pyvenv.cfg` as state `"venv"`. `stata_venv` then runs pip into it, both for "using the environment already there" and for a re-run while linked (:670-690).
- Today, `bokeh>=3.8` is a no-op on an installed 3.10.
- With `bokeh>=3.8,<3.10`, pip DOWNGRADES it to 3.9.x. That breaks 4d's "never downgraded behind the user's back".
- The claim "verify becomes a guard" holds only for a new venv.

Decide between:
- (a) Downgrade, but only in a venv dash created. In a reused venv, check first and report `above` without installing bokeh.
- (b) Always pass the ceiling and document the downgrade.

Recommend (a).

### C6. The `above` hint must follow the N4 managed-Python rule (gap)
