## 2. Sub-claims at HEAD

### 2a. No concurrent-session cap: STILL TRUE
- The only session gate after the key is `_SESSION_LIMITER.is_allowed`, a per-minute rate (dash_render.py:34165-34168; template make_document 34741-34752). The defaults are 60 per client, 60 new clients and 600 in all, per minute.
- Nothing counts open sessions. `on_session_destroyed` and `max_sessions` appear nowhere in dash_render.py.
- Measurement (m2_live.py: a live `python app.py`, 200k rows x 3, one scatter, 25 held `pull_session`s):
  ```
  server up, rss=221MB
  session 1: roots=1 1.87s rss=357MB
  session 10: roots=1 1.60s rss=1061MB
  session 24: roots=1 1.99s rss=2016MB
  session 25: roots=1 1.78s rss=1842MB
  ```
  All 25 sessions were served, and the server grew by about 70-100 MB per session.

### 2b. No unused-session lifetime: PARTLY TRUE (the wording is inexact)
- dash sets neither `unused_session_lifetime_milliseconds` nor `check_unused_sessions_milliseconds` (the Server(...) template at dash_render.py:36482-36490). Bokeh's defaults therefore apply. On bokeh 3.8.0 and 3.9.0 they are 15000 ms and 17000 ms.
- Bokeh discards a session only when `connection_count == 0` (bokeh/server/contexts.py `_cleanup_sessions`).
- So a page-only session (an HTTP GET with no websocket) is discarded after about 17-20 s. A connected session, such as an open or background tab, is never discarded, however long it sits idle. That second case is the real gap: there is no idle lifetime for connected sessions.
- Measurement (m3_expiry.py: in-process server built by the app's own `_dash_server_app`, one held websocket session plus one page-only GET):
  ```
  unused_session_lifetime_ms 15000 check_unused_ms 17000
  t=   0s sessions=2 connections=[1, 0]
  t=  15s sessions=2 connections=[1, 0]
  t=  20s sessions=1 connections=[1]
  t=  50s sessions=1 connections=[1]
  ```
- m12_destroy.py confirms that `doc.on_session_destroyed` fires for both kinds:
  ```
  [('created', 0.6), ('created', 0.7), ('destroyed', 17.0), ('destroyed', 34.0)]
  ```
  The page-only session went at 17 s. The websocket closed at 2.9 s, and its session went at 34 s.

### 2c. Each session re-decodes the whole dataset: STILL TRUE
- Template make_document calls `spec, df, meta = _load_spec_and_data()` (dash_render.py:34754). That decodes `_DATA_B64` from base64, parses the JSON, builds rows and a DataFrame, and reads the columns (34572-34647).
- m1_cost.py and m6_mem.py, at 200k x 3:
  ```
  _load_spec_and_data 0.39s
  make_document #1 0.96s  #2 0.98s  #3 1.03s   (maxrss 625 -> 690 -> 771 MB)
  _load_spec_and_data retained 4.6 MB, peak 84.4 MB
  make_document doc retained 60.7 MB, peak 84.4 MB
  ```
- The decode is about 40% of a session's open time, plus an 84 MB transient peak.
- The retained 60.7 MB per session is mostly not the frame. m7_mem.py (tracemalloc, by line of the generated app) shows:
  - 22.9 MB for `_orig_src_data[id(_s)] = {c: list(v) ...}`, the per-session snapshot list copies.
  - 12.2 MB for `_dash_column_values(...).tolist()`.
  - 7.6 MB for `_pdata['index'] = list(_pdf.index)`.
  - 4.6 MB for the DataFrame itself.
  Every session holds the same initial values, so all of these could be shared.

### 2d. One event loop blocked by recomputes
- **lowess: STILL TRUE.**
- **lpolyci: FIXED by WP-29 P0.9.**
- Recomputes run synchronously inside the on_change callback on the IOLoop, through `_dash_event_throttle`, which calls `fn` inline (dash_render.py:24384-24396). The help says so itself (dash.sthlp:1779-1780: "one process, one event loop -- runs one recomputation at a time for every session together").
- m1_cost.py (100k rows; a scatter plus the layer; a dropdown move to about 50k rows):
  ```
  lowess : make_document #1 28.38s ; filter move to 0.0: recompute 8.72s
  lpolyci: make_document #1 1.31s  ; filter move to 0.0: recompute 0.92s
  ```
- m2_live.py health (live server, lowess at 100k; /health polled while one session opens):
  ```
  session open 37.90s; /health polls=7 worst latency=37.09s
  ```
- m5_move_health.py (in-process server, the same app; /health polled after a client's filter move):
  ```
  session opened at 30.4s
  /health took 8.11s at 8.1s after the move
  ```
- The 27.7 s for lowess reproduces (28.4 s). The 8.7 s for lpolyci does not: lpolyci now takes 1.3 s per session and 0.9 s per move. 8.7 s matches a lowess move to half the rows, so the source probably mislabelled it.

## 3. twoway's truth

twoway has no server, sessions or event loop, so there is no twoway behaviour to match for the cap, the lifetime or the decode. The one comparable quantity is the estimators' own cost.

t1_cost.do, run through scripts/stata_slot.sh, StataNow 19.5 MP, 12 processors, load average 13-23:
```
. twoway lowess y x, nodraw              timer 1:  54.55
. twoway lowess y x if g == 0, nodraw    timer 2:  11.83
. twoway lpolyci y x, nodraw             timer 3:   0.91
. twoway lpolyci y x if g == 0, nodraw   timer 4:   0.62
```
- dash's lowess (28 s, and 8.7 s on half the rows) is no slower than Stata's. lowess is O(N x window) by definition (BUGS.md:1286).
- The gap is therefore architectural: a shared loop and unbounded sessions. It is not an estimator gap. No Stata truth fixture is needed.
- Not measurable here: Linux and Windows (Docker is broken and there is no VM). The approach below uses only portable stdlib threading and public Bokeh API.

## 4. Approach

Split the item into two plan sections.

### P1.31a: Session capacity and memory (yellow, M)

All of 31a lives in `ServerAppBuilder._generate_app_source` (the app template) unless named otherwise.

1. **Decode once per process.**
   - New template helper `_dash_shared_payload()`. It decodes `_SPEC_B64`/`_DATA_B64` once and caches `(spec, df, meta)` in a `sys.modules` holder keyed by sha256 of the two literals. This is WP-29's `_dash_process_key` pattern, so `bokeh serve`, which re-runs the module for every session, also shares the cache.
   - Make every numpy array in the frame and in `qual_masks` read-only. An in-place write in any session then raises instead of leaking into other sessions.
   - Give each session `copy.deepcopy(spec)` and copies of the small meta dicts.
   - make_document calls it in place of `_load_spec_and_data()` at 34754. Keep `_load_spec_and_data` as the loader.
2. **Concurrent-session cap.**
   - Add the launcher flag `--max-sessions N` (default: decision D1).
   - Count at make_document after the key gate and the rate limiter. Release through `doc.on_session_destroyed` and on idle close, guarded so a session is released once.
   - Past the cap, serve a Div page like the 429 page: "Server busy: N dashboard sessions are open; close one or wait about half a minute" naming the flag. Log the refusal once a minute per limit, as `_RateLimiter` does.
   - Keep the counter in the same process holder.
3. **Idle lifetime for connected sessions.**
   - Add `--session-idle-minutes M` (default: decision D2; 0 means never).
   - Every throttled callback (filter, brush, CSV) stamps `last_active` through a wrapper at the three call sites (template 36098, 36186, 36218). Do not edit `_dash_event_throttle` itself.
   - A per-session periodic callback runs the pure function `_dash_idle_due(last_active, now, minutes)`, which takes a clock for tests.
   - When a session is idle past its lifetime: remove its periodic callbacks, `doc.clear()`, add a Div telling the user to reload the page, and release its slot.
   - Measured with m10_leak.py: after the document is synced, `doc.clear()` frees the session's data.
     ```
     session 1: live 60.7 MB, after clear 10.2 MB, after the doc is dropped 10.1 MB
     ```
     The leftover 10 MB is constant across sessions, not a leak. Without the sync, the model manager's `_new_models` set keeps the data, so a test must call `doc.models.flush_synced()` as a live server does.
4. **Explicit Bokeh lifetimes.** Pass `unused_session_lifetime_milliseconds` and `check_unused_sessions_milliseconds` to `Server(...)` in `_dash_server_app` (template 36482). Suggested values are 15000 and 5000, so a closed tab frees its place in about 20 s rather than up to 34 s. Both are public keyword arguments on bokeh 3.8.0 and 3.9.0.
5. **Warm-up and estimator memo.** This removes the 28 s per-session lowess build after the first session.
   - Add a process-wide, byte-bounded LRU memo `_dash_estimator_memo` around `GlyphMapper._stata_lowess`, the expensive pure estimator. Optionally add `_fp_fit` and the lpoly kernels.
   - The memo key is a blake2b hash of the input arrays plus every parameter. Results come back read-only.
   - The app rebinds the copied class's staticmethod, so the saved renderer is untouched.
   - In the `python app.py` `__main__`, build one throwaway Document before `_server.start()`. This fills the decode cache and the memo, and prints one line when it takes over 2 s.
   - The launcher already waits for /health, and shows `_no_answer_shown`.
6. **Optional, and could go to P2.41 instead.** Share the initial-source snapshot (`_orig_src_data`, 22.9 MB per session at 200k) as read-only arrays per (graph, source position) instead of `list(v)` per session.
7. **Plumbing and help.**
   - `main` (dash_render.py:37560-37680) and `_dash_launch_app` (37206; argv at 37318-37326) pass the new flags.
   - dash.ado `_dash_serve` syntax (8294-8301) gains `maxsessions()` and `idletimeout()`, validated digits-only like port() and timeout() (decision D1). argv is built at dash.ado:8454.
   - The `dash build, server` "Limits:" line (dash.ado:8240) lists the new flags.
   - The launcher banner line "Session limits per minute" (template 36591) gains them too.
   - dash.sthlp changes:
     - The flag list (1606-1611).
     - The bokeh serve caveat (1636-1641), which follows decision D3.
     - The limits section (1740-1771), which gains a "Sessions open at once" paragraph and the idle rule.
     - The dash serve options table (857-874).

### P1.31b: Recompute off the event loop (red, L)

1. **Move the compute to a worker.**
   - Split the template's `_make_filter_cb._on_filter_change` (template about 25392-25617 in a generated app), and the brush recompute, into three steps:
     - Read the widget state and build the masks on the loop (cheap).
     - Compute every `_dash_redraw_for(...)._redraw(frame)` result and KPI value in a process-wide `ThreadPoolExecutor(max_workers=1)`. This keeps today's documented one-recompute-at-a-time rule, but off the loop.
     - Apply the source copies through `doc.add_next_tick_callback`, which is Bokeh's documented thread-safe entry.
   - A per-session generation counter drops stale results.
   - An in-flight flag folds events that arrive during a compute into one trailing recompute with the latest values, the same semantics as the throttle's trailing call.
   - Show a small "updating" cue while a compute runs (decision D4).
2. **Keep in-process builds synchronous.** When `doc.session_context is None` (tests, warm-up, ServerAppBuilder), the recompute stays synchronous, so `test_mode_parity` and every existing served test keep their meaning. Separate live tests prove that the asynchronous final state equals the synchronous one.
3. **Measured feasibility.**
   - m8_thread.py: lowess on 50k rows in a worker thread left an asyncio loop ticking (1080 ticks, worst delay 78 ms, median 1.5 ms). On the loop thread, the same lowess blocked it for 7.4 s.
   - The compute slows under GIL sharing: 13.1 s against 7.4 s at load average 13.
   - A process pool is not viable. `dash serve` hands the app over as text (`-P -c _DASH_BOOT`), so spawn cannot re-import it, and fork is unavailable on Windows.
4. **Thread-safety audit (the risk).**
   - `_DASH_NOTED` is a module-global set, cleared per make_document (dash_render.py:15350-15360).
   - The app contains 8 `warnings.catch_warnings` blocks. These are not thread-safe before Python 3.14's context-aware warnings.
   - `_STORAGE_TYPES.update` and `_graph_qualifiers.update` mutate module globals per session.
   - Each must be shown to be untouched by the worker, or made per-call. `np.errstate` is thread-local and safe.

## 8. Decisions for the maintainer

- **D1. Cap value, and whether `dash serve` exposes it.** Options: (a) a launcher flag only, default 20; (b) the flag plus `dash serve, maxsessions(#)`; (c) no default cap (opt-in). Implications: at 200k x 3 a session holds about 60-100 MB, so 20 sessions is about 2 GB, and the cap is the only bound on total memory. Recommendation: (b), default 20.
- **D2. Idle lifetime default, and what counts as activity.** Options: (a) 60 minutes, server-observed activity only (filter, brush, CSV); (b) 0 (never) by default, opt-in; (c) a client heartbeat (CustomJS) so that pan, zoom and hover count. Implications: (a) can close a tab that is only being looked at; (c) adds JS under CSP. Recommendation: (a) with a clear reload message, and `idletimeout()` on dash serve.
- **D3. Do the cap, idle limit and memo apply under `bokeh serve`?** Today the help says the app's limits do not apply there (dash.sthlp:1638-1641). The sys.modules holder (WP-29's key pattern) makes it possible. Recommendation: yes, apply them, because memory exhaustion is the threat. Update the caveat.
- **D4. Off-loop recompute (31b).** Options: (a) a worker thread: the old layer shows until the new result arrives, with an "updating" cue; (b) keep blocking and document it. Implications: (a) carries thread-safety risk (module-global notes and `catch_warnings`); (b) leaves /health and every other session frozen for the length of a lowess (8-38 s at 100k). Recommendation: (a) with one worker.
- **D5. Warm-up at launch.** The banner and the first page wait for the initial compute (about 28 s for lowess at 100k), but no session ever pays it. The alternative is that the first session pays it. Recommendation: warm up.
- **D6. Per-client concurrent cap (GAPS2 F3 plan).** With the key gate and loopback binding, every client is usually 127.0.0.1. Recommendation: no per-client cap; the global cap is enough.

## 9. Effort, risk, split, feasibility

- Effort: L overall (31a M, 31b L).
- Risk: 31a yellow (HIGH-risk generator, but additive and testable in process); 31b red (concurrency in a 37.7k-line generator with module-global state).
- Split: yes, into P1.31a (cap, idle, decode once, lifetimes, memo and warm-up, flags, help) and P1.31b (off-loop recompute). 31a can ship alone and closes three of the four sub-claims. 31b closes the loop-blocking claim.
- Feasibility here: high for both. Everything is measurable on macOS with Stata's Python (bokeh 3.8) and Homebrew's (bokeh 3.9) through in-process servers and `pull_session`; no browser is needed. Windows and Linux stay unmeasured (UNCLEAR, P1.34).

## Critic additions

Checked at HEAD c96facd, read-only. Scratch: `<scratchpad>/wp30/c-p1-31/k1.py` (Stata's Python, bokeh 3.8.0).

### Spot checks (both hold)
- **Decode per session, recompute inline.** k1.py, lowess at 20k: 3 make_documents gave `decode_calls=1, 2, 3`. A dropdown move ran the estimator on the calling thread (`estimator threads=['MainThread']`), and the assignment returned only after the 0.43 s recompute. lpolyci at 100k: the move took 0.80 s, so lpolyci is FIXED.

### Errors in the note
1. **Wrong function for the dash.ado options.** The syntax at dash.ado:8294-8301 and the digit checks (8307-8337) belong to `_dash_serve_spec` (rclass, 8272), not to `_dash_serve` (8369). `_dash_serve_spec` returns `r(port)`/`r(timeout)` (about 8356-8360), and `_dash_serve` reads them into argv (8455). So `maxsessions()`/`idletimeout()` need three edits: syntax and validation plus new `return local` lines in `_dash_serve_spec`, and argv in `_dash_serve`. Add `_dash_serve_spec` (UNKNOWN: ado is not indexed) to §6.
2. **Wrong `main`.** The flags pass through the `if __name__ == "__main__"` block: argparse at 37557ff, then the `_dash_launch_app(...)` call at about 37672. `def main` (36823) only writes the app and needs no change. `gitnexus impact main` is **UNKNOWN**: four `main` symbols match, and only the dash_render.py one is LOW (7). The `__main__` block is not a graph symbol.
3. **Missing template symbols.**
   - The app's own CLI is `_dash_arg_parser` (template 34457) and `_dash_apply_limits` (34508), not "the launcher".
   - `_dash_limit_value` (34440) refuses 0. `--session-idle-minutes`, where 0 means never, therefore needs its own type function.
   - Some new helpers may be module functions copied into the app the way `_dash_event_throttle` is: `_dash_idle_due`, the memo, or `_dash_shared_payload` if it is unit-tested outside an app. These go in the copy list of `ServerAppBuilder._glyph_layer_lines`, which is **HIGH** (4 impacted, 4 processes; P1.30 calls it a hot spot).
4. **The test plan contradicts itself.** §5 says the cscript refuses `0` for both `maxsessions()` and `idletimeout()`. §4.3 and `TestIdleSessionsAreClosed` say 0 means never, which is also the existing `timeout(0)` rule (dash.sthlp:874). `idletimeout(0)` must pass, and only `maxsessions(0)` is refused.

### Gaps in the approach
6. **In-process documents must be exempt from the cap.** `on_session_destroyed` never fires when `doc.session_context is None`. Three kinds of document would take slots that are never released and then get the busy page:
   - the warm-up Document (§4.5);
   - P1.26's build-time trial (`make_document(Document())`, p1-26.md:197);
   - every in-process test that calls make_document more than N times on one loaded app.

   The key gate already passes such documents (`_dash_session_token_ok`, dash_render.py:4120-4122). The cap needs the same rule, plus a test.
7. **The decode cache must be bounded and must stay out of Stata's process.** A `sys.modules` holder keyed by the sha256 of the literals keeps every distinct payload for the life of the process. Two places make that a leak:
   - P1.26's trial execs the app inside Stata's embedded Python (main() runs under runpy). Each `dash serve` or `dash build, server` would then leave a decoded frame, and the memo, in Stata for the whole Stata session.
   - A pytest xdist worker loads hundreds of apps.

   Rule: hold one entry (replace on a new key), and skip both the cache and the memo under `_DASH_TRIAL` or when the module is not served. Add a test for each.
8. **Interaction with P1.26 (cost twice).** At 100k lowess, P1.26's trial in Stata's Python costs about 28 s (p1-26.md:209). 31a's warm-up in the child repeats it, so `dash serve` waits about 56 s before the first page. The plan must choose one:
   - the trial skips estimator layers;
   - the child's warm-up serves as the trial (WP-29 already forwards child stdout, so its notes reach Stata);
   - or accept the doubling, and document it.
9. **A warm-up over 30 s looks like a failure.** `_dash_launch_app` (`ready_seconds=30.0`, 37207; 37473-37480) prints "no answer from .../health after 30 s; still waiting". §4.5 prints its line only "when it takes over 2 s", which reads as after the build. The app must print a "preparing the dashboard (N rows, lowess)" line before the warm-up starts, and a launcher test should pin the order.
10. **31b leaves session open on the loop.** make_document runs on the loop for every new session. That is 1.6-2.0 s at a 200k scatter (§2a m2), and 3.1-4.6 s at a 100k scatter plus lpolyci (k1.py, load average above 10). Warm-up and the memo remove only the estimator part. Record this as a residual, or state the bound: up to `max-sessions` opens at once means up to cap x open-time of blocked loop.
11. **No global recompute budget.** GAPS2 F3 plan item 3 asks for a global recompute budget, and the note neither adopts nor rejects it. With one worker and folding, the queue is bounded by the number of open sessions. The worst wait is still cap x recompute: 20 x 8.7 s is about 3 min at 100k lowess. D4 must state this bound and any fairness rule.
12. **The F3 memory test is dropped.** GAPS2 F3 test 5 says N `pull_session`s must grow RSS "much less than the data size per session". The note has no RSS test. Its own numbers show that decoding once saves only about 4.6 of the 60.7 MB each session keeps (§2c). The per-session lists stay:
    - `_orig_src_data`, 22.9 MB (step 6 is optional);
    - `.tolist()`, 12.2 MB;
    - `list(_pdf.index)`, 7.6 MB.

    Either give the test a realistic bound, or hand it to P2.41 explicitly (D7 below).
13. **The saved page is out of scope, but say so.** It has no sessions, loop or decode, and its fitted-line redraw on a filter move is a separate gap (GAPS2 C intro). The plan should say so in one line. It should also require that the saved page is unchanged: `test_mode_parity`, the stat_truth lowess values, and a byte comparison of one saved page before and after, because the memo and the shared helpers sit beside the saved renderer.
14. **Thread-safety audit (31b): missing items.**
    - `_dash_redraw_for._redraw` builds Bokeh models in the worker: `bokeh_figure()`, `_dash_draw_layer` renderers and ColumnDataSources (template 35086-35090). This is safe only because nothing on that path calls `curdoc()`: in dash_render.py, `curdoc()` appears only at template 36413, and Bokeh's patched curdoc is process-global, not thread-local. Pin that with a test.
    - P1.26 B2's process-wide `showwarning` replacement is another global that the worker's `warnings.warn` reaches.
    - An idle close (31a) while a worker compute is in flight must bump the generation, so that the result is dropped.
