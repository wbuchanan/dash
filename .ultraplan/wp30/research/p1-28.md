## 4. Both modes, and after a filter move

- The toolbar is shared. `_dash_name_save` runs on every grid in the saved page (dash_render.py:25020, 25083, 30963, 32533) and in the served app's generated source (:36293, :36346). The served app copies `_DASH_FIGURE_TOOLS`, `_DASH_SAVE_NAME` and `_DASH_SAVE_NAME_RE` by name (:33028-33029, inside `_glyph_layer_lines`). An action added there reaches both modes, provided any new constant is added to that list.
- A client-side SVG (or PNG) save exports **what is on screen**:
  - Saved page: after a filter move, the CustomJS-filtered views (with the WP-29 stale cue on frozen layers).
  - Served app: after a move, the server's recomputed sources.
  - This matches today's PNG save. It is not measured live on a server here. The served document can be tested the way `test/test_by_scales_chrome.py::_served_page` (:48-53) tests it, by rendering the served doc with `file_html` before and after a server-side move.
- A headless `dash export` (option C) would export the page as built: filters at full extent and the first tab active. It cannot reproduce a viewer's filter state. Document this.
- `r(filename)` is mode-specific:
  - The saved page's path (one-line `saving()`, the preview path, or `dash build, saving()`).
  - The `.py` for `dash build, server saving(app.py)`.
  - Nothing for `dash serve`: its app is deleted on exit, and the URL carries the WP-29 key, which must never be returned (M4, "the key is never printed").

## 5. Proposed approach

Split in two (see §8). Part A needs no new dependency and is independent of the decision. Part B is the export route the maintainer chooses.

### Part A (P1.28a): results and guards

1. **`dash` becomes rclass and returns `r(filename)`** (dash.ado:84 `program define dash, rclass`).
   - Each writer stores its path in one global, `dash__rfile`, which `dash` clears at entry and drops after `return local filename`:
     - `_dash_render_immediate`, beside dash.ado:6830;
     - `_dash_build`, beside :8229 and :8243.
   - Use a global, not `c_local`, because `_dash_render_immediate` is two calls below `dash`.
   - The value is the path as the "saved to" message shows it, so message and `r()` agree.
   - Because `dash` is rclass, every leaked internal `r()` (`r(fn)`, `r(open)`, `r(flag)`, `r(value)`...) is replaced on exit. `dash clear`, `dash kpi` and a registration leave `r()` empty.
   - `dash serve` returns no `r(filename)` and never a URL.
   - Grep confirms no test reads `r()` straight after a `dash` call. Every `r(fn)`/`r(open)`/`r(ceiling)` read in test/*.cscript follows a direct helper call (`_dash_find_render`, `_dash_limit`, `_dash_browser_wanted`), e.g. test_bug_regressions.cscript:435, :458; test_adversarial.cscript:905; test_help_claims_4.cscript:461.
2. **Stale-graph note** (decision D2): in the one-line form and in `dash build`, after the page is written, run `quietly graph dir, memory`. If `r(list)` is not empty, say once through `_dash_say`: "dash: graph export writes Stata's current graph (Graph), not this dashboard". Name the graph from `graph describe`'s `r(fn)`. This closes the *silent* half of claim b. It changes no graph memory, so HC1-12 (test_help_claims_1.cscript:731-755) still holds.
3. **`saving()` with an image extension** (decision D3): extend the `.gph` rule at dash.ado:6478-6489 to `.png .svg .pdf .eps .ps .jpg .jpeg .tif .tiff .gif .emf .wmf`. Replace the extension with `.html` and note "saving() writes HTML, not an image; using x.html; use the toolbar's save button". This shares the paragraph with P1.27.
4. **Help** (dash.sthlp):
   - Add a `{marker results}{title:Stored results}` section: `r(filename)`, per route, and that `dash serve` stores none.
   - In Differences item 1 (:446-450) and Exporting (:980-986), say that `graph export` does not see a dash figure and writes Stata's current graph if there is one, and say what the export route is.
   - Add a Jump To entry (J8's test, `test_help_claims_1.py:187`).
5. CHANGELOG ("Results that change": `r()` after dash; the saving extension note), and a BUGS.md entry for the `r(fn)` leak and the silent stale export.

### Part B (P1.28b): the export route (recommended B1 and B2; B3 optional; B4 not recommended)

- **B1. Save as SVG on every toolbar, both modes (M).**
  - Add a JS constant `_DASH_SVG_SAVE_JS` and, in `_dash_name_save` (dash_render.py:24445), append one `CustomAction(description="Save as SVG", callback=CustomJS(args={grid: model, name: filename}, code=_DASH_SVG_SAVE_JS))` to a grid's toolbar. The filename is the same `_dash_save_filename(name)`, so the result is `dashboard.svg`, or `g1.svg` under `layout(bs)`.
  - Add the constant to the served app's copied-name list (dash_render.py:33028).
  - The code wraps `export("svg")` in try/catch and shows a visible message on failure (E11 pattern).
  - Use the existing save icon variant or `icon=` with a data: URI (CSP `img-src data:`).
  - Keep the PNG save as it is.
  - The KPI cards, title, filters and tab strip stay out of the image, as for PNG; document this.
- **B2. Print stylesheet (J7-b), deferred.** Bokeh `Tabs` do not lay out inactive panels, so CSS alone cannot print them. Document "printing prints the active tab". A real fix needs `beforeprint` JS that lays out every panel (M, unmeasured).
- **B3. `dash export using file.{png|pdf|svg} [, replace width() height() scale() tab()]` (L, optional).**
  - New dispatcher route (dash.ado:118-133) and program `_dash_export`. It builds the saved page to a private temp file (reusing `_dash_tmp_open`/`_dash_private_write`).
  - It calls a new renderer function, `_dash_headless_export(page, out, fmt, width, height, scale, chrome)`, with this Chrome handling:
    - Find Chrome as `test/responsive_probe.py::find_chrome` (:123) does, plus Edge and Windows paths.
    - Accept a `$DASH_CHROME` override only if it is an absolute, regular, executable file, run with no shell.
    - Use a 0700 temp profile. `--headless=new`, no network (the page CSP is `connect-src 'none'`).
    - PNG via `--screenshot`, with the toolbar hidden by an injected style. PDF via `--print-to-pdf`. SVG via `--dump-dom` with an injected `export("svg")` script.
    - Use a **watchdog**: poll for the output and kill Chrome after N s, because measured Chrome 154 never exits on its own.
  - Refusals, in twoway's words where twoway has them:
    - eps, ps, tif, gif, emf: r(198), with the T4/T10 messages.
    - No browser found: r(601) "dash export: no Chrome, Chromium or Edge found; set $DASH_CHROME or use the toolbar's save buttons".
  - `r(filename)` is the output path. It cannot be tested off macOS (P1.34 deferred under M4).
- **B4. `twoway` companion option (GAPS2 J7 step 1), not recommended now.**
  - `dash ..., twoway` would re-issue `twoway <the command without hover(), saving(.html), name()>`, so that `graph export`, putdocx and dyndoc see a Stata-drawn twin. It is cheap (about 0.09 s per draw, U6).
  - But it draws twoway's look, not dash's.
  - It fails on every option dash notes and twoway refuses (U3-U5), until the "refuse vs note" decision lands.
  - It cannot represent a `dash build` dashboard.
  - If it is on by default, it flips HC1-12.
