The renderer never reads either key (`_apply_mlabel_opts`, dash_render.py:9302-9500). It uses one `mlabposition` for the whole layer (:9466-9478). The immediate path discards the option (`opts.pop("mlabvposition", None)`, :14417).

The served app shares this applier. Its inertness is pinned by existing tests:

These are `TestAnUnsupportedOptionIsInertWhenServed` (served) and `test_a_plot_option_reported_unsupported_really_is` (saved). Both must be flipped.

### 2d. "No test checks declared options reach the spec": still true

- test_option_surface.cscript O2-01..O2-10 checks only return codes and the note.
- test_unsupported_report_is_true.py feeds the renderer hand-written specs and asserts that nothing changes. It never runs dash.ado's serialiser.
- test_twoway_option_parity.py:270-274 checks only that `sort1` is not written.
- No test compares the declared syntax with the `_dash_plot_opts_to_json` key list.

### 2e. Side effect: repeated `mlabvposition()` is accepted

twoway refuses a second copy. `_dash_rep_unique` already lists `mlabvposition` (dash_parse.mata:4695-4704). However, `_dash_opts_repeats` finds an option's key through its `s()` (`_dash_rep_keyof`). Because `mlabvposition` sets no `s()`, the second copy is not caught. Measured: `dash scatter y x, mlabel(lab) mlabvposition(p9) mlabvposition(pos)` gives rc 0 and a note. twoway gives r(198), "option mlabvposition() not allowed".

## 4. Proposed approach

Two halves. They can ship separately (see section 7).

### 4a. `mlabvposition(varname)`: both modes, before and after a filter move

**dash.ado**
1. `_dash_parse_plot_opts`:
   - Add `sreturn local mlabvposition : copy local mlabvposition`.
   - Remove the `_dash_pending' mlabvposition` line (:1079) and its WP-22 comment.
   - Once the option sets an `s()`, `_dash_opts_repeats` can find its key, so the existing `_dash_rep_unique` entry refuses a second copy with r(198), as twoway does. Test this explicitly.
2. `_dash_plot_opts_to_json`: add `mlabvposition` to the key list.
3. A new `_dash_fold_mlabv <ptype>` (sclass), called from `_dash_fold_bw` next to `_dash_fold_mlab` and before `_dash_validate_opts`. It reads `s(mlabvposition)` by value, then:
   - On histogram, function, scatteri, pci and pcarrowi, it blanks the value. twoway never reads it there.
   - On the 21 types twoway refuses (rarea, rbar, rcap, rcapsym, rconnected, rline, rscatter, rspike, tsrline, lfit, qfit, fpfit, lfitci, qfitci, fpfitci, lowess, lpoly, lpolyci, kdensity, mspline, mband), it exits 103 when the variable exists. The message follows the `_dash_fold_mlab` precedent: `dash: mlabvposition() is not allowed on <ptype> (twoway: too many variables specified)`. A variable that does not exist falls through to r(111). The refuse-or-note choice is a decision; see section 6.
   - It refuses a non-name with r(198) "invalid name", and more than one name with r(103) "option mlabvposition(): too many names specified", in twoway's words and codes. The shared `var` rule would give r(111) and r(198) instead.
4. `_dash_option_rules`: add `mlabvposition=var`. It checks that the variable exists (r(111)) and normalises an abbreviation (`po` becomes `pos`).
5. Types that accept the option but draw no label (line, spike, area, pcspike, tsline) keep the value and draw nothing. Like `mlabel()` there, they do not name it in the note.

**dash_parse.mata**
- `_dash_extract_vars`: add `"mlabvposition"` to `keys` so the variable reaches the data JSON on the immediate route and the build route (dash.ado:6532, :7619).

**dash_render.py**
1. `_DASH_OPT_VAR_KEYS` becomes `("colorvar", "mlabel", "mlabvposition", "wexp")`. Every column consumer goes through `_dash_option_columns`, so this alone carries the column in both modes:
   - saved column lists (:1446, :1517, :29087)
   - the embed plan (:28168)
   - served `extra_cols` (:34844, :34980, :34998)
2. `GlyphMapper._apply_mlabel_opts`: when `options["mlabvposition"]` is a Stata name (`_dash_is_stata_name`) and the source has that column:
   - Derive four per-row columns that always exist, named from the variable with a reserved prefix. Suggested names: `__dash_mlabel_<var>_vpx`, `_vpy`, `_vpa` and `_vpb`. The offsets are numpy float arrays and the align/baseline values come from a fixed table, so no user text reaches them (keep them as arrays, P2.41).
   - Fill them from `_MLABEL_CLOCK`:
     - A whole number 0..12 gives that clock.
     - Missing, `.a`-`.z` or a non-numeric (string) column gives the layer's fallback position (`mlabposition()`, else 3).
     - Any other finite value (3.5, 13, -1) gives 12, with one `_dash_warn_once` note per layer naming the distinct values. Cap the list (for example, the first 10 values and a count).
   - Apply `mlabgap` along each row's own unit vector.
   - Point the LabelSet's `x_offset`, `y_offset`, `text_align` and `text_baseline` at those fields.
   - Like the text column (:9377-9395), compute the columns from the source on every call. A served mapper redraw then rebuilds them, and a refreshed linked source reads them from the snapshot by row. Both are existing behaviours for `__dash_mlabel_*` (`_dash_refresh_linked` :24732, `_dash_refresh_unlinked` :24849).
   - On the saved page, `_FILTER_JS` filters every column of every graph and derived source by row. The snapshot is taken after the figures are built (:32072-32080, :32207), and label copies are collected by `_collect_derived_sources` (:29662). The per-row columns therefore stay aligned after a move.
3. `GlyphMapper._pc_clean_with_label` (:13957-13990) copies only `mlabel` and the row id. It must also copy the `mlabvposition` column, for pcarrow and pcbarrow. The other label call sites (map_scatter's view subset, map_bar, map_dropline, map_pcscatter, map_pccapsym) build their sources with `_carry_cols` or `_subset_source`, which copy every column. Verify each with a test.
4. `_immediate_labels` keeps `opts.pop("mlabvposition", None)`. twoway ignores the option on scatteri and pci (measured).

**Help (dash.sthlp)**
- Add `mlabvposition(varname)` to "Marker Label Options" (:2146-2185) with the measured rules: precedence over `mlabposition()`, missing and string values, out-of-range values, the types it draws on, and the types where it is refused.
- Remove it from the Unsupported section "Marker-label placement and text style" (:3704-3709). test_help_claims_8.py:1492-1497 checks that this section equals the pending list.

### 4b. `mlabtextstyle(textstyle)`

- dash.ado: add the `sreturn`, add the JSON key, and remove the pending line (:1078). Do not refuse it on any type (twoway accepts it everywhere).
- dash_render.py: generalise `SchemeParser._NOTE_TEXTBOXES` (:6751-6766) into one textbox-style table (name to size key and colour key) used by `note()` and marker labels. Add `p#` (`p#label` size and colour, with `#` the layer's pstyle index).
- In `_apply_mlabel_opts`:
  - A known style sets `text_font_size` from `scheme._gsize("gsize <key>")` and `text_color` from `scheme._color("color <key>")`.
  - An explicit `mlabsize()` or `mlabcolor()` overrides the style in either order (measured).
  - An unknown name gives the note "named style X not found…" and the textstyle defaults (the "body" size and black, as measured).
- The starting point (no option) is the `p#` style. That is P1.4's "marker-label size and colour are fixed at 10px #444444", so this half depends on P1.4 (see section 5). Size units follow the P1.12 decision.
- Help: document it in Marker Label Options and remove it from Unsupported.

## 7. Decisions, effort, risk, split, feasibility

**Decisions only the maintainer can make**
