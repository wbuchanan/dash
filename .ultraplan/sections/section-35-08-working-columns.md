## Overview

**What is wrong today.** Audit DT-19: "Variables named __dash* give r(110); dash's working columns can give r(900) at c(maxvar)". twoway draws data holding a variable named `__dashq1` (probe Q11: rc 0); dash refuses it: `_dash_qual_gen` (dash.ado:7917) opens with `capture unab _dq_clash : __dash*` and exits 110 with "variable ... is named with the prefix __dash, which is reserved for the columns dash makes ..." (:7920-7926); `_dash_sort_gen` (:8054, message :8066), `_dash_tsop_gen` (:8112, :8128) and `_dash_wexp_gen` (:8201, :8213) repeat it. The renderers refuse a reserved-prefix column the spec does not name (`_DASH_RESERVED_PREFIX = "__dash"`, dash_render.py:59310; `_dash_take_qual_columns` :59545). And the four Stata-side families (`__dashq#`, `__dashs#`, `__dasht#`, `__dashw#`) are generated in the user's frame, so a dataset near `c(maxvar)` is refused r(900) by `_dash_maxvar_room` (dash.ado:7856) where twoway, which needs only its own few tempvars, draws. dash.sthlp:211-226 documents the reservation and :239-243 the r(900).

**After this section.** (1) dash's column names are chosen per command so that none equals or prefixes a variable of the data -- of any frame the build reads, a graph registered under Stata's `frame f:` prefix included (D-35-08.c): the reserved prefix `R` is `__dash` when no variable of those frames -- and, on the build route, no value-label set of them -- starts with `__dash`, else the first of `__dsh1_`, `__dsh2_`, ... that none starts with; every Stata-made and renderer-made column uses `R` (`R+"q"+k`, `R+"_row__"`, `R+"m_"+var` ...), 33-07's split columns and value-label copies included (`R+"m"+k` for its `__dashm<k>`, `R+"l"+j` for its `__dashl<j>`, D-35-08.c), and the spec carries `R`. (2) When the user's frame has no room for the working columns beside the dataset's variables, they are generated in a temporary frame holding only the variables the export needs (`frame put`), so `c(maxvar)`'s room is the room beside those variables, not beside the whole dataset; with room, the columns are made in place as today. In a build whose graphs come from several frames (33-07), each frame is planned on its own, and its temporary frame is put from that frame (D-35-08.c). A variable named `__dash...` is then data like any other, as in twoway. (3) A qualifier or weight naming `e(sample)` reads the estimation sample on both branches, as twoway reads it (today's export reads it after `_estimates hold` and keeps no row; measured 20oct2026, D-35-08.b).

### Section decisions

- **D-35-08.a The prefix is per command**, computed once in dash.ado at export time (`_dash_reserved_prefix`, TR-35-08.1), written to the master spec as the top-level key `"_dash_prefix": "<R>"`, and read by both renderers at their one data-loading entry through `_dash_prefix_of(spec)`; JavaScript reads it from the config it already receives (`pl.key` is passed today; the missing-code prefix becomes a config key).
- **D-35-08.b The frame only when room is short** (REVIEW R2-10). A new pure program `_dash_maxvar_plan n k kx maxvar` decides from four numbers: `inplace` when `n <= maxvar - k` (today's path, unchanged: the columns are made in the user's frame); else `frame` when `n <= maxvar - kx` (kx = the variables the temporary frame would hold); else `refuse` (r(900) in today's words with kx added, TR-35-08.3). `_dash_maxvar_room` calls it with `c(k)`, `c(maxvar)` and the counts it computes today. Only the `frame` branch makes a temporary frame: `frame put <varlist>, into(<tmp>)`, where `<varlist>` is the export varlist (`needed_vars` on the one-line route, `all_vars` on build/serve; dash.ado:11832, :13255) plus every variable the qualifier, sort, time-series and weight expressions name (`unab` over the names `_dash_qual_gen`, `_dash_sort_gen`, `_dash_tsop_gen` and `_dash_wexp_gen` read; `_dash_extract_qual_vars` for the qualifiers) plus the `tsset`/`xtset` panel and time variables, plus the `e(sample)` copy `<R>esample` when the export made one (below); the time-series settings are re-applied in the frame (`tsset <panelvar> <timevar>, delta(<tdelta>)` from `quietly tsset`'s r() read before the put); the export then runs inside the frame and the frame is dropped on every exit path. **e(sample).** twoway reads `e(sample)` as the estimation sample in the frame the estimation ran in and as 0 in every other frame, and `_estimates hold` makes it 0 everywhere (measured 20oct2026 with this plan's probe: after `regress mpg weight if foreign`, `count if e(sample)` is 22 in that frame, 0 under `frame f2:` and 0 after `_estimates hold`; `frame f2: twoway scatter mpg weight if e(sample), nodraw` is rc 0). The internal global `$dash__force_frame` (`1`) makes the plan answer `frame` whatever the room, so certification exercises the frame branch without `set maxvar` (REVIEW R2-11); after each `frame put` the frame branch appends the name of the frame it put from to the internal global `$dash__frame_trace`, so a certification case sees that the branch ran (a byte-equal data file alone would also pass if it never did).

## User stories

- **US-35-08.1** As a Stata user whose data hold a variable named `__dashq1` (or `__dash_row__`), I want dash to draw my graph as twoway does.
- **US-35-08.2** As a user with a wide dataset near `c(maxvar)`, I want a dashboard that uses a few variables to be built, as twoway draws it.
- **US-35-08.3** As a Stata user, I want `dash scatter mpg weight if e(sample)` after an estimation to draw the estimation sample, as twoway does.

## Business requirements

- **BR-35-08.1** No variable name is refused for its prefix; a variable named exactly like any dash column is drawn, hovered, filtered and downloaded as its own data.
- **BR-35-08.2** A dataset whose exported variables leave room for the working columns is not refused for the dataset's other variables; a dataset with room is exported exactly as today, except that a qualifier or weight naming `e(sample)` reads the estimation sample (BR-35-08.4).
- **BR-35-08.4** A qualifier or weight naming `e(sample)` keeps the rows twoway keeps: the estimation sample in the frame the estimation ran in, none in any other frame, whether the columns are made in place or in a temporary frame.
- **BR-35-08.3** Saved and served pages agree; nothing in a tooltip, filter, table or CSV names a working column.
