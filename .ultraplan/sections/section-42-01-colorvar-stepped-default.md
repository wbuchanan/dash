# Section 42-01: Unbinned numeric colorvar binned at the z ticks; key width from the scheme

> Part of: WP-42 (Colour variables, audit package 7) · Items: CV-8 (DT-22, sil:SD-20), sil:SD-4 (sil:SD-14) · Risk: yellow · Batch: 42.1 · Depends on: none · Blocks: 42-02, 42-05 · Tasks: 4, 2 commits · Case-id prefix: Q4201

## Overview

**What is wrong today.** An unbinned numeric `colorvar()` on every coloured type that is not a line -- scatter, dot, bar, rbar, spike, rspike, dropline, rcap, rcapsym, rscatter, rpcap, rpspike, pcspike, pccapsym, pcarrow, pcbarrow, pcscatter -- is mapped through a 256-colour `LinearColorMapper` and keyed by a gradient `ColorBar` (dash_render.py:16737-16753, `palette = _rule_palette(256)` :16744, `ColorBar(... width=12 ...)` :16751-16752). The audit (CV-8, appendix colorvar-family): "An unbinned numeric colorvar is cut at the z-axis ticks at or above the minimum, giving n+1 levels in n+1 rule steps ... Price gives 4 colours #0000ff #00ffaa #aaff00 #ff0000 (K10, T7). Under s1mono: #bfbfbf #808080 #404040 #000000 (I7)", while "Under the mono schemes the lowest value is #fefefe on a white plot region, which is nearly invisible". Only a line (`stepped=True`, `_colorvar_line_parts` :17150) and the markers of connected/rconnected (:18563, :23560, :23568) take twoway's levels through `_colorvar_stepped_mapper` (:17059). The colour bar is a fixed 12 px (`width=12` :16752; contour's `cb.width = 12` :24622) where twoway draws the scheme's `gsize clegend_width` (s2color `huge`, scheme-s2color.scheme:185; measured about 23 px on a 5.5 in graph, audit sil:SD-4), and the scheme's contour keys `yesno contours_outline`, `contours_colorlines`, `contours_reversekey` and `numstyle contours` (scheme-s2color.scheme:56, :2238-2240; read by twoway through style/zyx2style-default.style `set ownlines scheme contours_outline` ...) are never read (sil:SD-14).

**After this section.** Every continuous `colorvar()` layer, on every type twoway colours, is drawn in twoway's levels: the cuts are the key's ticks at or above the domain's minimum, n cuts give n + 1 levels in n + 1 colours of the rule (or `colorlist()`), a value on a cut takes the level below. The key is a stepped bar of those colours ticked at the key's ticks, the zero label of `colorvar(price)` included. After a filter move both modes cut the kept rows again (a new relevel kind, saved JS and served Python twins). The bar's thickness is the scheme's `gsize clegend_width` (and its length `gsize clegend_height` when not zero), on the colorvar key and on contour's key; the scheme's contour keys are read as twoway reads them, by measurement. The help sentence "How the colours are drawn is dash's" (dash.sthlp:5523-5533) is replaced.

**Why one section.** Both items are the colour bar's default form, built in the same continuous branch of `GlyphMapper._apply_colorvar`, and 42-02..42-05 build on the stepped default.

**Test order and commit rule.** Two items, two commits, in manifest order. CV-8: 42-01-01 writes the extract script and every CV-8 regression test and saves the failure text (no commit); 42-01-02 makes them green, flips the pins, appends the cscript block and commits `(WP-42 CV-8)`. sil:SD-4: 42-01-03 writes its regression tests and saves the failure (no commit); 42-01-04 makes them green and commits `(WP-42 sil:SD-4)`. No full suite inside the section.

### Section decisions

- **D-42-01.a The stepped path is the only continuous path.** `_apply_colorvar`'s continuous branch always calls `_colorvar_stepped_mapper` when the mapper is a `LinearColorMapper` or `LogColorMapper` and the bar has ticks, whatever `stepped` says; the `stepped` argument stays (callers pass it) and from now on only decides whether `self._colorvar_step_plan` (the line's pool plan) is recorded. `colpalette()` is refused at the Stata side since WP-35 (35-07, ruling P4-7), so only a hand-written spec still reaches `_cof`'s even sampling (:16794-16797); leave that branch as it is (42-05 pins the refusal).
- **D-42-01.b The bar draws twoway's axis range.** The glyphs keep the mapper `_colorvar_stepped_mapper` returns (bins moved up by `eps`, closed above). The `ColorBar` gets its own mapper of the same palette with `low = cuts[0] - step` and `high = cuts[-1] + step` exactly (no `eps`), so a tick on `low` (price's `0`) lies inside the bar and is drawn. Both mappers are kept on the plan.
- **D-42-01.c A new relevel kind `stepmap`.** A continuous marker/bar/spike layer records `renderer._dash_cvar = {"kind": "stepmap", ...}` (the line pool's kind `steps` stays as it is). Python twin `_dash_cvar_relevel_stepmap(plan, dom)` and JS twin `dash_cvar_relevel_stepmap(pl, dom)` in `_DASH_CVAR_RELEVEL_JS`; both re-tick the bar (`_dash_cvar_key_ticks` / `dash_cvar_key_ticks`), cut, and rewrite the two mappers' palette, low and high, by the arithmetic of `_dash_cvar_relevel_steps`' mapper block (dash_render.py:52548-52557).
- **D-42-01.d The key's form stays a ColorBar here.** twoway's side title, axis line and swatch shapes (DT-22's second half) are the key-cell work of 42-03 (CV-3, LT-22), which replaces this bar for every binned key; CV-8 closes on the colours, the levels and the stepped bar. The BUGS resolution names 42-03 for the key's form.
- **D-42-01.e Scheme widths.** `SchemeParser` reads `gsize clegend_width` and `gsize clegend_height` through `_gsize_units` (dash_render.py:11361) into `self.clegend_width_rs` and `self.clegend_height_rs`; the bar's thickness in px is `max(1, round(rs * OptionTranslator.PT_PER_RS * 4 / 3))` -- 2.88 pt a unit, the 4-inch reference every other dash size uses. The scale post-pass `_dash_apply_scale` (:27529; its ColorBar branch :27587-27590) does not multiply a bar's `width` today; 45-04 adds it when it scales the unit. `clegend(width())` still wins (`_colorvar_key_place` :16903-16916). A `clegend_height` of 0 (s2color) leaves Bokeh's length ("auto").
- **D-42-01.f Contour keys by measurement.** The extract script measures each of `contours_outline yes`, `contours_colorlines yes`, `contours_reversekey yes` and `numstyle contours 4` in a user scheme that includes s2color, against s2color itself. A key twoway draws differently becomes the default of the matching contour flag (`outlines`, `colorlines`, `reversekey`, `levels()`) when the user gives none; a key twoway ignores is documented in the help ("read and ignored, as twoway ignores it"). Measured 20oct2026 in this section's scratch probe (sandstone, `twoway contour depth northing easting`): `numstyle contours 4` leaves `.plot1.lastcuts` at `7700 7800 7900 8000`, the default's, so `numstyle contours` changes nothing; the extract script re-measures it.

## Risk: [yellow] -- the default picture of every non-line colorvar plot changes, with a new saved-page twin

**Why.** The continuous default is the feature's main use; every pinned test that reads a 256-colour palette or a gradient bar flips; the relevel after a move gains a kind in two languages.

**Risk factors.** 1. `_apply_colorvar` is 700 lines shared by every mapper; the stepped mapper also replaces `mapper` for `zscale(log)` (its log branch, :17084-17105). 2. A date colorvar: the bar's ticks are in column units (epoch ms) after `_dash_key_ticks`; `_colorvar_stepped_mapper` compares them with `lo`/`hi` in column units -- consistent, but pinned only for lines (test_date_axis_residuals.py). 3. The JS twin must match the Python twin row for row. 4. Tests that read `len(mapper.palette) == 256`.

**Mitigation.** 1. The regression tests cover log, date and zlabel() forms on scatter. 2. Reuse `_colorvar_stepped_mapper` unchanged except D-42-01.b's extra bar mapper. 3. A node test through `test/js_runner.py` and a parity move entry (R8). 4. The flip list in Evidence is built by running the named files at the base (42-01-01) and every failure is flipped with a `Flipped:` line.

## User stories

- US-42-01.1 As a Stata user with an existing twoway command, I want `dash scatter mpg weight, colorvar(price)` to colour the cars in twoway's four levels with a stepped key so that the picture matches twoway's.
- US-42-01.2 As a Stata user, I want a mono scheme's colorvar markers to start at #bfbfbf, not near-white, so that every point is visible.
- US-42-01.3 As a dashboard author, I want the levels and the key to follow a filter move in both the saved page and the served app.
- US-42-01.4 As a Stata user with my own scheme, I want its `clegend_width` and contour keys read as twoway reads them.

## Business requirements

- BR-42-01.1 A continuous colorvar on every coloured non-line type draws twoway's level colours (each fixture probe's distinct colours equal, and for scatter the observation partition equal).
- BR-42-01.2 The key shows one colour per level, labelled at twoway's key ticks, including a tick below the data's minimum.
- BR-42-01.3 After a filter move the kept rows are cut again, saved and served alike.
- BR-42-01.4 The key's thickness follows the scheme; `clegend(width())` still wins.
- BR-42-01.5 The scheme's contour keys draw what twoway draws with them; nothing is printed for them.
