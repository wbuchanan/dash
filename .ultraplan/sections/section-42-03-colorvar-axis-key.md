# Section 42-03: twoway's axis-style colour key

> Part of: WP-42 (Colour variables, audit package 7) · Items: CV-3, CV-15 (LT-23), LT-12, AX-12 (syn:SD-4), LT-22 · Risk: red · Batch: 42.4 · Depends on: 42-02, 42-05 · Blocks: 42-04 · Tasks: 10, 5 commits · Case-id prefix: Q4203

## Overview

**What is wrong today.** dash's colour key is a Bokeh `Legend` (discrete and binned keys, dash_render.py:16581-16698, `Legend(items=legend_items, title=var_display, name=_COLORVAR_LEGEND_NAME)` :16698) or a `ColorBar` (continuous, :16751; contour, `_contour_key` :24607). twoway's key is a column of swatches beside a z axis. The audit:

- **CV-3:** "(1) The highest level is at the top ... (2) Labels are z-axis ticks, not level names ... Binned keys label the cut values between the swatches ... (3) There is no missing or 'Other' entry ... (4) There are no value labels unless zlabel(, valuelabel) ... (5) The swatch takes the plot type's key: a rect for bar and spike, a line for line types." dash: ascending entries (1 at the top), value labels or interval texts ('1–2.33333', '≤2'), a '(missing)'/colorotherlabel entry, circle swatches for every type (Quads under colorkeysrange), a black frame.
- **CV-15 (LT-23):** "On a discrete key, zlabel(1 3 5) relabels the key (C24), zscale(reverse) puts 1 at the top with colours to match (C26), and zlabel(, valuelabel) shows Domestic/Foreign at the ends (K7). clegend(region()), clegend(altaxis) and clegend(width(abc)) are drawn (P2-P4)." dash names them ("... is not a recognised sub-option; using not drawn", `_colorvar_key_place` :16917-16918; `_DASH_CLEGEND_SUBOPTS` :53239-53241 has only position ring width height title off on).
- **LT-12:** `clegend(title("Z"))` replaces the key's z title, and `clegend(title("Z", box))` draws the text '"Z", box' (`_dash_clegend_opts` :53271-53272 takes the whole argument unquoted; `_colorvar_key_place` :16898-16899 sets `key.title`). twoway adds 'Z' above the key and keeps the rotated z title.
- **AX-12 (syn:SD-4):** `zlabels()`, `zticks()`, `zmlabels()`, `zmticks()` are refused (twoway takes them; twowaygraph_g.class:125-126 declares `ZLabels ZTicks ZMLabels ZMTicks`); `ztick()`, `zmlabel()`, `zmtick()` are noted and not drawn, and are missing from the help's Unsupported list (dash.ado:995 and :1324 declare only `ZLABel ZTItle ZSCale`).
- **LT-22:** contourline with `colorlines` draws no level legend (twoway keys 8000..7700); plain contourline prints a needless note (dash.sthlp:592-593); the contour key's title sits above with no axis line.

**After this section.** Every colour key -- colorvar's discrete, binned and stepped continuous keys, contour's and contourline's -- is twoway's axis-style key: a key cell of swatches in the plot type's key style (rect, line or marker), highest level at the top, a z axis with an axis line, ticks and labels at twoway's ticks (natscale for a discrete key, the cuts for a binned key), the title running up the axis side, no missing entry, no frame; zlabel()/zscale()/the z tick family and every clegend() sub-option twoway draws are drawn on it; contourline under colorlines draws its level legend. Both modes, before and after a filter move.

**Why one section.** All five items are the colour key's form, built once as a shared composite.

**Test order and commit rule.** Five items, five commits, in manifest order (CV-3, CV-15, LT-12, AX-12, LT-22); each item is a tests task (no commit) then a fix-and-commit task.

### Section decisions

- **D-42-03.a The key cell.** A colour key is a bare Bokeh `Plot` (no toolbar, no outline, no grid, `background_fill_alpha 0`) built by a new module-level function `_dash_key_cell(spec)` from a key spec dict `{"levels": [(lo, hi, colour)], "kind": "rect"|"line"|"marker", "marker": <Bokeh marker>, "ticks": [...], "labels": {pos: text}, "minor": [...], "mlabels": {...}, "title": text, "title_opts": {...}, "side": "right"|"left"|"above"|"below", "reverse": bool, "log": bool, "width_px": int, "length_px": int|None, "region": {...}, "subtitle"/"note"/"caption": ...}`. The cell is `sizing_mode="fixed"` and tagged `dash_key_cell`, and its outer `width` (a key above or below: `height`) is numeric at build: new `_dash_key_cell_extent(cell, band_px)` returns `band_px` plus the axis allowance, estimated as `_dash_frame_borders` and `_dash_overhangs` estimate borders -- `major_tick_out + major_label_standoff + ceil(n * 0.6 * px)` (n the longest tick label's characters, px the label font in px, `OptionTranslator.css_to_pt(axis.major_label_text_font_size) * 4 / 3`; for a key above or below `ceil(px)` in place of the label width), plus `ceil(tpx) + 10` when the axis has a title (tpx its font in px, `_dash_frame_borders`' title allowance), plus `ceil(axis_line_width)`; `band_px` is `spec["width_px"]` (42-01's scheme clegend_width or clegend(width())), kept as `cell._dash_key_band`, with `cell._dash_key_len = spec["length_px"]` and `cell._dash_key_side = spec["side"]`. The cell's other side (`height` for a key at the right or left, `width` above or below) is the figure's when the figure is fixed (set at wrap time, TR-42-03.3); when the figure stretches it starts at the figure's `height` (`width`) and `_DASH_KEY_CELL_JS` writes it from the figure's drawn `outer_height` (`outer_width`) with the borders. The swatches are glyphs on a `ColumnDataSource` (`Quad` for rect, `Segment` for line, `Scatter` for marker) spanning their level on a `Range1d` z range; the axis is a `LinearAxis` (or `LogAxis` under zscale(log)) on the cell's right (left under `altaxis`) with a `FixedTicker(ticks, minor_ticks)`, `major_label_overrides`, `axis_line_*` drawn, `axis_label` the title, `axis_label_orientation` reading upward on the right (the radian sign measured in 42-03-01 in Chrome). Placement: `fig._dash_key_cell = cell`; `_dash_layout_cell` (dash_render.py:51524) wraps the figure and its cell in `row(fig, cell)` (right or left) or `column` (above or below) by the clock, in both modes (it is shared by grid, tabs and the served app); a layout-time CustomJS `_DASH_KEY_CELL_JS` sets the cell's `min_border_top`/`min_border_bottom` (or left/right) to the figure frame's offsets so the z axis spans the plot region, on `inner_height`/`outer_height` changes.
- **D-42-03.b ring(0).** A key inside the plot region (`ring(0)`) is drawn by the same spec on two extra ranges of the figure (`fig.extra_x_ranges["dash_key"]`, `extra_y_ranges["dash_key"]`) chosen so the key occupies the clock's corner at `clegend_width` by the frame's height less `bmargin()`; swatches as glyphs, ticks as a `Segment`, labels as a `LabelSet`, the title a `Label`. Measured placement from the extract script's `P_bp_*` probes.
- **D-42-03.c Which keys.** colorvar keys built by `_apply_colorvar` (discrete, binned, stepped), the contour key (`_contour_key`, which also draws 37-02's degenerate-surface key, DG-8), 37-01's empty contour key (`GlyphMapper._contour_key_empty`, DG-1: a key with no rows), 41-04's by() colour key under coloruseplegend with clegend(on) (`_dash_by_colour_bar_cell`, BY-14, which left its z-axis styling to this section), and contourline's (LT-22). Every one of them becomes a key cell; none stays a ColorBar. `coloruseplegend` keeps a Legend in the plot legend (twoway's plegend is a legend box; 42-04's CV-4). A key on a by() graph: `_dash_by_keys`' colour-key handling (grep `_COLORVAR_LEGEND_NAME` in the by() code, :55703-55752) takes `fig._dash_key_cell` where it took the Legend/ColorBar model.
- **D-42-03.d Relevel.** The key cell's source and ticker are on every plan (`plan["keycell"] = {"src": ..., "ticker": ..., "axis": ..., "range": ...}`); new Python twin `_dash_cvar_keycell_update(plan, levels, colours, ticks, labels)` and JS twin `dash_cvar_keycell_update` are called by every relevel kind (range, stepmap, steps, bins, levels) after it computes its levels. This section edits `_DASH_CVAR_RELEVEL_JS`; it is alone in batch 42.4 (DECISIONS A-11) and the manifest marks it JS = yes.
- **D-42-03.e The swatch kind per type** is measured (extract script `S_<type>`: the key's swatch element kind for each coloured type) and stored as `_DASH_KEY_SWATCH_KIND = {type: "rect"|"line"|"marker"}` (constant, copy list).
- **D-42-03.f clegend(title())** is parsed with `_parse_textbox_opt` (its text and textbox sub-options) and drawn as a `Title` above the cell, the z title staying on the axis.

## Risk: [red] -- a new composite replaces every colour key, in the layout, both modes and the move twins

**Why.** Colour keys are pinned by many tests (Legend items, ColorBar models); the layout function is shared by grid, tabs and the served app; the relevel JS gains a key update for five kinds.

**Risk factors.** 1. Layout: a row/column around a figure changes what `_dash_layout_cell` returns (export, link groups, by(), table under the figure). 2. Frame alignment depends on JS at layout time. 3. Many pinned tests read `fig.select({"type": ColorBar})` or the `_COLORVAR_LEGEND_NAME` Legend. 4. Saved-page SVG export of a row: `_DASH_SVG_SAVE_JS` exports `find_one(grid)` -- the cell must be inside the exported grid. 5. Accessibility (axe) and CSP: the cell is a plain Plot, no new script source beyond a CustomJS (hash/nonce path unchanged).

**Mitigation.** 1. `_dash_layout_cell` wraps only when `fig._dash_key_cell` is set; a figure-only test asserts the old return for every key-less figure. 2. A Chrome test reads both frames' bounding boxes (test/range_probe.RangeProbe) and asserts the z axis spans the plot region within 2 px. 3. The flip list is produced by 42-03-01's base run and each pin flipped with its reason. 4. test_export_svg.py runs in the section. 5. test_csp.py, test_csp_browser.py, test_accessibility*.py run in the section.
