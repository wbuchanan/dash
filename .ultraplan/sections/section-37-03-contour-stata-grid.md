# Section 37-03: Contour from twoway__contour_gen for gridded data or interp(none)

> Part of: WP-37 (Statistical and computed layers) · Items: TR-13 · Risk: red · Batch: 37.3 · Depends on: 37-02 · Blocks: none · Tasks: 4, 1 commit · Case-id prefix: Q3703

## Overview

**What is wrong today.** The audit (package 12, TR-13 with stat:PT-19 and sil:SD-19, audit :646-648; appendix :2584-2589, :1161-1166, :2774-2779): "contour above 1,000 distinct points fits a seeded subsample on a 100x100 grid (every sandstone help example); a repeated node keeps the smallest z; a different polygon cutter". All 8 `twoway_contour.sthlp` and 5 `twoway_contourline.sthlp` examples use `sysuse sandstone` (6,400 points on a regular 80 x 80 grid) and print "(note: dash: contour draws an approximate surface: 6400 distinct points exceed the 1000 ...)": `_dash_contour_surface` (dash_render.py:29137) fits a seeded 1,000-point subsample on a 100 x 100 grid above `_DASH_CONTOUR_EXACT_MAX = 1000` (:13992-14003). twoway itself calls `twoway__contour_gen` (ado/base/t/twoway__contour_gen.ado, v1.0.15) from `zyx2view_g.class` `reset_dserset` (:252-346) on the plot's serset -- under `by()` once per panel, on that panel's serset.

**Research.** [S] §6: `twoway__contour_gen zvar yvar xvar [if] [in], cuts(numlist) [gen(z y x levels)] [line] [heatmap] [interp(string)]` replaces the dataset with polygon vertices in rows, one polygon per run of rows separated by an all-missing row; filled: `levels` is the band index 1..k+1 for k cuts; line: one polyline per run, `levels` the cut index 1..k, `z` the cut value. On sandstone (gridded) it takes 0.23 s (filled, 32,689 rows) or 0.09 s (line, 598 rows), whatever `interp()`; on gridded data `interp()` does not change the output. On scattered points it grows about as n^4 with the default thinplatespline (400 points 143 s; 1,000 points twoway's own draw unfinished after 12 minutes), but `interp(none)` stays fast (100 points 0.03 s, 400 points 0.86 s). Cuts are computed only when twoway draws: `ccuts()` when given, else from `levels()`, else the z axis's ticks (sandstone default `7700 7800 7900 8000`; levels(10) `7606.5 7657 ... 8010.5`).

**What will be true after.** Ruling M9 / C3 (Q26 narrowed) and P4-7 (the syntax and the picture mirror twoway's): when a contour or contourline layer's data is a full grid, or `interp(none)` is given, dash runs `twoway__contour_gen` itself at export, with twoway's cuts, and draws its polygons -- so every sandstone example draws twoway's own contours; with `outlines`, `alpattern()` or `sort`, the bands' boundary lines are drawn from the same generator's lines at those cuts, never over the placeholder grid the renderer is built on (D-37-03.h). Under `by()` the same rule is applied to each panel's own rows, as twoway runs its generator once per panel, and each panel draws the polygons made from its rows (M9 makes no by() exception: sandstone by() panels are full grids). A graph registered in another frame under Stata's own prefix, `frame <F>: dash contour ..., name()` (33-07; DECISIONS A-17: dash takes no `frame()` option), is drawn the same way from its own frame's rows (P4-4). Scattered data with any other `interp()` keeps today's fit (exact up to 1,000 distinct points, the seeded subsample and its note above). After a filter move both modes do the same (DECISIONS A-26, Q26): while the layer (or the panel) still has every row the generator was given they draw Stata's polygons with no cue; once a move leaves a row out they draw dash's own fit of the kept rows and show the stale cue -- the served app by re-running the mapper on the moved rows (REVIEW R3-4), the saved page through its existing JS twin of that fit (`dash_contour_surface` and the cutter, WP-31 B4c), which fits up to 1,000 distinct kept points; above that the saved page keeps Stata's polygons, marked (D-37-03.g). A layer too small for a surface (fewer than four points, or fewer than two distinct x or y) never reaches the generator, so 37-01's empty contour and 37-02's key without a surface are unchanged (REVIEW R3-5).

### Section decisions

- **D-37-03.a At export, not at registration (ruling M9).** The generator runs where every other layer's data is read -- after the qualifier columns exist, on the data in memory at `dash build`/`dash serve`/the one-line command (dash.sthlp:190-205's rule) -- so a registered contour draws the build-time data like its siblings. Index M9 says it: "Contour from `twoway__contour_gen`, run at export (dash evaluates data at build)"; Q26's "at registration" is superseded by it.
- **D-37-03.b Cuts are twoway's, computed in Stata.** `ccuts()` → its numlist, sorted; else `levels(#)` with # >= 2 → `zmin + i*(zmax-zmin)/#`, i = 1..#-1, plus zmin and zmax under `minmax`; else the z axis's ticks as twoway's z axis has them: no `zlabel()` or `zlabel(#N)` → Stata's `_natscale zmin zmax N` (N = 5 by default) ticks; `zlabel(<numlist>)` (including `a(b)c`) → Stata's `numlist` expansion; then the interior ticks (first and last dropped when there are more than two), as `_dash_contour_cuts` (dash_render.py:29227-29261) drops them; and `[zmax]` when none is left. Any other `zlabel()` form (`minmax`, `none`, a list with labels) → the Stata grid is not used and today's fit draws the layer. Under `by()` the cuts are computed once, over the first panel's rows (the first by() group in by() order, the panel twoway draws first), and used for every panel and the Total panel, since twoway cuts every by() panel at its first panel's z axis (the rule 41-01 records for BY-28); task 01's by() probe measures each panel's cuts (TR-37-03.1, `first_panel_rule`), and where the fixture shows each panel cut at cuts of its own rows instead, task 02 computes the rule above over each panel's own rows (the Total panel's over all of them) -- the fixture decides and the hand-back says which rule it showed; `ccuts()` gives one list either way. The cuts go to the renderer with the polygons and the renderer draws the bands and the key from them (TR-37-03.5). Task 01 records, per probe, whether they equal `_dash_contour_cuts`' on the same data; where they differ, twoway's own cuts win (the key is labelled at the object's cuts), and the hand-back lists those probes.
- **D-37-03.c The channel.** The grid object `{"cuts": [...], "line": 0|1, "x": [...], "y": [...], "z": [...], "levels": [...], "n": N}` (null where Stata has missing; `n` the number of rows the generator was given, for the served redraw and the saved page's refit, R3-4, D-37-03.g), plus, on a filled object whose layer has `outlines`, `alpattern()` or `sort`, the member `"lines": {"x": [...], "y": [...], "z": [...], "levels": [...]}` -- the generator's `line` output at the same cuts over the same rows (D-37-03.h) -- is keyed by the layer's place k beside the graph's function points: an external Mata table filled at export, appended by `_dash_fn_spec_tail` as a top-level member `"contour_grids": {<graph name>: {<k>: <value>}}`, where `<value>` is the grid object for a graph without by(), and under by() `{"panels": [{"key": [<the panel's by() values>], "grid": <object>}, ...], "total": <object>}` (`total` only under `by(, total)`; a panel the gate keeps out, or whose generator fails, has no entry). The key is the panel's by() values, as 37-04's D-37-04.e keys a fit's panels, written by 37-04's `_dash_fit_panel_key`, never the panel's place: the renderers leave out panels twoway leaves out after grouping. `_dash_attach_function_points` (renamed nothing; it gains the member) puts the value in the layer's options as `options["contour_gen"]`, and both renderers give each by() panel its own entry through `_dash_contour_panel_spec` (TR-37-03.5), keyed with 37-04's `_dash_by_key_of`. No size check: P4-3 (33-15, batch 33.1) removed the page-size cap `$dash_max_bytes`, so the polygons are counted against nothing; Q3703-1 records the sandstone page's size in the hand-back (REVIEW R3-22's measure, without a cap).
- **D-37-03.d Drawing Stata's polygons.** The ContourRenderer is still built with `fig.contour` over the stub grid and the layer's fill levels (so its key, its sources and the served pairing are unchanged), then `cr.set_data(ContourData(fill_data=FillData(xs, ys, lower_levels, upper_levels), line_data=LineData(xs=[], ys=[], levels=[])))` replaces its data with Stata's polygons. When Stata's polygons come in non-decreasing `levels` order (task 01 measures it on every probe; the renderer checks each object), band b's item holds each of Stata's polygons with `levels == b` as one single-ring polygon, `lower_levels[b-1], upper_levels[b-1]` the band's bounds from the fill levels -- band order is then twoway's painter's order. Otherwise the fill data holds one item per Stata polygon in Stata's row order, each with its band's bounds and its band's colour (TR-37-03.5), so twoway's painter's order is kept. contourline: `LineData(xs, ys, levels)` with each level's runs joined by NaN. `bokeh.plotting.contour.ContourData`, `FillData`, `LineData` and `ContourRenderer.set_data` exist with these fields in Bokeh 3.8.0 and 3.9.0 (checked 20oct2026); `set_data` copies every fill column other than `xs`, `ys`, `lower_levels` and `upper_levels` (`fill_color` among them, one entry per band) from the old data (read in bokeh 3.9.0's source, 20oct2026).
- **D-37-03.e Scope.** Under `by()` the generator runs once per panel (D-37-03.c's keyed object; D-37-03.f's gate applied to each panel's rows), and once over all the layer's rows for the Total panel under `by(, total)`, as twoway's `zyx2view_g` runs it per panel. Not for `heatmap` (twoway uses `twoway__heatmap_gen`, a different generator; today's heatmap cells stay). `horizontal` swaps each ring's x and y, as the grid is transposed today; date planes convert each ring through `_on_axis` as the grid's `gx`/`gy` are.
- **D-37-03.f Who reaches the generator (REVIEW R3-5).** A layer -- under `by()`, each panel of it, and the Total panel -- goes to `twoway__contour_gen` only when it has N >= 4 selected rows, at least 2 distinct x and 2 distinct y, and either passes the grid test or has `interp(none)` (with `interp(none)`, N >= 3 and the same 2 x 2 distinct values). Below that the layer (or the panel) takes today's path (37-01's empty contour, 37-02's degenerate key). A generator error is not a refusal dash has measured: the frame is dropped, nothing is printed, and the layer (or the panel) is drawn with dash's own fit, as if the generator had not been tried.
- **D-37-03.g After a filter move (DECISIONS A-26; Q26: "after a filter move dash refits with its own fit and shows the stale cue").** One rule in both modes, keyed on the object's `n`: a layer (or panel) whose kept rows with finite z, y and x number `n` -- every row the generator was given, since a move only removes rows -- draws Stata's polygons and key with no cue; fewer rows draw dash's own fit of the kept rows, cut as a dash-fitted layer is cut after a move (`_contour_refit_rule`), with the stale cue. Served: `map_contour` decides it on each redraw (TR-37-03.5(b)). Saved: the layer is handed to the page's refit as a layer within the cap is (`_dash_agg_*`, WP-31 B4c), its config carrying `stata_n` = `n`, and the contour branch of `_FILTER_JS` gains one write-back step for such a config (TR-37-03.5(d)): it keeps the build's source data and colour-key state on its first run (as the lpoly branch keeps `src._dash_built`, dash_render.py:34887) and writes them back instead of refitting when the kept count equals `stata_n`, or when `dash_contour_surface` returns null because more than the cap's 1,000 distinct points are kept (:34171) -- there the page keeps Stata's polygons, marked, as decision D4 keeps an above-cap layer's build, while the served app draws its seeded subsample (the cap's existing mode difference; the help says so, TR-37-03.6). The cue is the one a fit drawn from Stata's own points shows -- kind "fit", the key suffix `_DASH_STALE_SUFFIX["fit"]`, the caption and the status line -- so the two modes write the same key text (TestTheRuntimeNotesAgree): on the saved page the layer's frozen tag takes kind "fit" (TR-37-03.5(c)) and shows when a move leaves out a row of the layer (the saved stale block's rule, dash_render.py:35189-35219); in the served app each renderer is marked `_dash_points_frozen` at build, so the app registers the layer's cue (`_generate_app_source_body`, :70528-70532), and `_dash_points_stale` on a redraw that drops the object (read at :71379-71381). No new JS twin, no new cue kind and no new cue text (Notes: the cue's wording).
- **D-37-03.h Boundary lines from the Stata grid (found while editing the plan; reported to the orchestrator).** `outlines`, `alpattern()` and `sort` draw the bands' boundaries (WP-32, `GlyphMapper._contour_parts` dash_render.py:24481-24575 at f81cd31): a second ContourRenderer, built with `fig.contour(x=gx, y=gy, z=gz, levels=<the cuts>, ...)` over the `grid` `map_contour` passes it, the lines at the cuts in `_style`'s colours, widths and dash. On a layer drawn from Stata's polygons that grid is the stub grid (`gx = gy = [0.0, 1.0]`, `gz` all NaN, TR-37-03.5(b)), so the boundary renderer would draw nothing. So, on such a layer, the boundary lines are Stata's: `_dash_contour_gen` runs the generator a second time, with `line`, at the same cuts over the same rows, and the object carries that output as `lines` (D-37-03.c); `_contour_parts` builds the boundary renderer over the stub grid as today and then `lr.set_data(ContourData(fill_data=None, line_data=LineData(xs, ys, levels)))` puts Stata's lines in it, item i holding the runs whose `levels == i + 1` (cut i + 1), so `_style`'s per-cut colours, widths and dash apply to them unchanged. `set_data` keeps the per-level `line_color`, `line_width` and `line_dash` columns of the stub build when the new LineData has the same number of levels (measured 21oct2026 in bokeh 3.8.0 and 3.9.0: a stub of three levels keeps its three entries of each). The lines at the cuts are what `_contour_parts` draws over dash's own fit; task 01's `sandstone.outlines` probe checks that twoway's boundaries are those lines and not the band polygons' rings (TR-37-03.1, `outlines_are_cut_lines`); a 0 there is written to the hand-back as a finding for the orchestrator (WP-32's rule on dash's own fit would then differ from twoway too, which is not this section's to change), and this section still draws the cut lines, so the two paths agree. A failed second call is a generator error (D-37-03.f): the layer (or panel) gets no object and is drawn with dash's own fit, boundaries included.

## Risk: [red] -- a new Stata generator at export and a new drawing path for contour

**Why.** The generator replaces the dataset (it must run in a frame); its output can be large (sandstone 32,689 rows); the renderer gains a second way to fill a ContourRenderer, a per-panel pick in both modes, and the saved page's contour refit a write-back step.

**Risk factors.** 1. Running the generator on the user's data would destroy it. 2. Scattered data with `interp(none)` above a few thousand points takes seconds to minutes. 3. A full-grid test that is wrong sends scattered data into an n^4 run. 4. The saved page's refit hand-over (`_dash_agg_*`, :24447-24464) gives a Stata-grid layer to the JS fit: a move that keeps every row of it, or more than the cap, must not leave dash's surface drawn unmarked where the served app draws Stata's polygons. 5. Mode parity compares saved and served drawings. 6. Under by() a panel's key in Stata and in the renderer must agree (numbers, strings, missing codes). 7. On 33-07's multi-frame build and 35-08's working frame the data is not in the user's frame.

**Mitigation.** 1. `frame put z y x if <sel>, into(<tmpframe>)` and the generator runs inside `frame <tmpframe>:`; the frame is dropped in every exit path (`capture noisily` around the block, drop, re-exit). 2. That is twoway's own cost, the user's choice (C3); the help says so. 3. The grid test is exact (TR-37-03.2): N rows with complete z, y, x; nx distinct x; ny distinct y; nx*ny == N and no repeated (x, y). 4. The layer's config carries `stata_n`; the contour branch writes the build back when the kept count equals it or the twin returns null above the cap, and the frozen tag (kind "fit") marks the layer whenever a move leaves out one of its rows (D-37-03.g); TestTheSavedPage runs the page's own script under node for the move, the move back and the cap. 5. Both renderers read the same `options["contour_gen"]`; the served app's first drawing is the same object, and a served redraw on fewer rows than the object's `n` drops it (TR-37-03.5); the MOVE_CORPUS entry and TestTheRuntimeNotesAgree compare the moved layer and its cue in both modes. 6. The keys are 37-04's: `_dash_fit_panel_key` in Stata, `_dash_by_key_of` in both renderers (pinned by 37-04's TestThePanels); Q3703-5 and TestTheRenderer::test_each_panel_takes_its_own_grid pin the contour use. 7. `_dash_contour_gen` runs under the frame prefix `_dash_write_data` runs under (TR-37-03.2), as 37-01's check does; Q3703-1's framed case pins it.
