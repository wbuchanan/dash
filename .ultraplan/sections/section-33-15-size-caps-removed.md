# Section 33-15: No size cap on a dashboard: the cell and page-bytes caps removed

> Part of: WP-33 (Verification corpus and README gallery) · Items: none (maintainer decision P4-3; closes no GAPS4 row) · Risk: yellow · Batch: 33.1 (beside 33-01; merged after it) · Depends on: none · Blocks: 33-06 (the limits table it extends), 33-07 (the build path it edits), 33-08 (no `$dash_max_bytes` to raise), 40-01, 40-02 · Tasks: 4, 1 commit · Case-id prefix: Q3315

## Overview

Today a dashboard is refused for its size. dash.sthlp:2947-2957 says `$dash_max_cells` counts "values the saved page embeds ... default 5,000,000, at most 20,000,000. Over it the build is refused with r(134) before anything is exported", and :2958-2966 adds `$dash_max_bytes`, "bytes of text embedded ... default 50,000,000, at most 500,000,000". Both languages enforce them: dash.ado's `_dash_cell_cap` (:5247-5284) prints `dash: this dashboard would embed <n> values (<shape>), more than the <limit> dash embeds.` and exits 134, `_dash_byte_cap` (:5306-5363) does the same for text, and the function points of a build are held to the bytes limit too (:13410-13426); dash_render.py re-checks both in the saved renderer (`_dash_refuse_oversized` :2805, `_dash_refuse_overbytes` :3167, called at :62218-62234) and the served builder (:68354-68404). A large part of the code exists only to count what a page embeds so the cap can be fair (GAPS2 G3, WP-29 P0.10, WP-31 G3): `_dash_embedded_cells`, `_dash_graph_computed_cells`, the Mata twins `_dash_computed_cells`/`_dash_graph_touched`, and the `row_vars`/`comp_cells`/`_byte_vars`/`_cap_vars` accounting on both Stata routes. The audit's plat:PT-7 (the cap counts every observation whatever if/in select) and plat:PT-8 (r(134) above 5M embedded cells) are about these caps.

The maintainer ruled (P4-3, 20oct2026): "No size cap on a dashboard. Batch 33.1 removes the embedded-cell cap (`$dash_max_cells`, 5M default, 20M ceiling) and the page-size cap (`$dash_max_bytes`, 50 MB / 500 MB) in both modes; the count caps (graphs, plots, by groups, tabs, filters, reflines, added text, table rows, images) stay and are documented (Q44)." After this section no dashboard is refused for the number of values or the bytes of text it embeds, on the one-line route, `dash build`, `dash build, server` and `dash serve`, in Stata and in both renderers; `$dash_max_cells` and `$dash_max_bytes` are no longer read (set or not, valid or not, they change nothing); every count cap is unchanged; the note dash prints above 1,000,000 embedded values (a report, not a cap) stays, counted from the rows and columns the page plan holds; the help's Resource limits section loses the two rows and its "What the data limit counts" paragraph, and says instead that a dashboard has no size cap. Every test that pins the two caps is flipped.

The section runs in batch 33.1 beside 33-01 because 33-06 (batch 33.2) extends the limits table and 33-07 (batch 33.3) edits the same build path; both build on the table and the path this section leaves. It touches none of 33-01's files (BUGS.md, GAPS4.md, test_tracking_documents.py, test_cscript_hygiene.py, test_packaging.py, run_all_cscripts.do, the truth-script template).

**Test order and commit rule.** Task 33-15-01 writes the regression tests (Python `TestNoSizeCap` and cscript cases Q3315-1..5), runs them against the unmodified tree and saves `<scratch>/33-15-01-failure.txt`; it commits nothing.
