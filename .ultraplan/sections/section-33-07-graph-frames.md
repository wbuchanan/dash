# Section 33-07: Registered graphs keep the frame they were registered in (Stata's frame f: prefix)

> Part of: WP-33 (Verification corpus and README gallery) · Items: none (new feature for the gallery, PD-12/C4, P4-4; syntax per P4-7) · Risk: red · Batch: 33.3 · Depends on: 33-06, 33-15 · Blocks: 33-08 · Tasks: 6, 1 commit · Case-id prefix: Q3307

## Overview

"One `dash build` draws one in-memory dataset; the corpus spans ~21 datasets" [C §4.1-4.2]: every registered command's qualifiers are re-evaluated at build on the data in memory, so a gallery page that mixes `sysuse auto`, `sysuse sp500` and the cached `webuse` files cannot be one dashboard today -- and "tempvar and frame graphs fail with r(111)" (audit ECO-1). C4 resolved it: "registered graphs keep their own frame so one `dash build` draws several datasets" (RESEARCH C4). PD-12 lists what such a build honours: "graphs in different frames may not share a `link()` or brush (refused r(198)); a filter applies to the graphs whose frame holds its variable; framed graphs support time-series operators, sort() and weight expressions like any other graph (P4-4)."

The syntax follows the maintainer's rule P4-7: "Unless the options are specific to functionality that only dash provides, the syntax should mirror twoway syntax as close as possible." twoway takes no `frame()` option; it draws from another frame under Stata's own prefix, `frame cars: twoway scatter mpg weight`. So dash takes the same prefix and adds no option: `frame cars: dash scatter mpg weight, name(g1)`. (P4-4's "frame()" names this feature; DECISIONS A-17 and index PD-12 spell it as Stata's own `frame f:` prefix, which dash replaces `twoway` in as everywhere else, and add no `frame()` option.)

After this section, `frame cars: dash scatter mpg weight, name(g1)` registers g1 in frame cars -- its variables are checked there, as `frame cars: twoway ...` checks them, which already holds today -- and dash records the frame: every named registration records the frame it ran in. At `dash build`, when every graph was registered in the build's current frame, nothing changes. Otherwise dash exports a stack: each graph's registry entry is read and checked in its own frame; for each frame, in registry order of first use, dash evaluates that frame's qualifier, time-series, sort and weight columns in the frame itself (so `in`, `_n`, `tsset`, `L.close`, `sort(date)` and `[aw=pop/1000]` mean what they mean there), keeps the variables that frame's graphs need, and appends the frames into one temporary frame; every plot of a graph from another frame is drawn only from its own frame's rows through a qualifier column; each filter is excluded from the graphs whose frame lacks its variable and applies to every graph whose frame holds it, a split column included, by that graph's own frame's values (DECISIONS A-27, PD-12); KPI cards read the build's current frame. The user's working frame never changes: every command that reads another frame runs under Stata's `frame <name>:` prefix. Both renderers see one dataset whose rows are selected by qualifier columns, which both modes already honour on every move; a variable two frames hold differently is the one thing they newly read per graph (next paragraph).

A variable that two frames' graphs both use keeps each frame's own storage kind, display format, value label and variable label (DECISIONS A-23): when they differ, the stack holds the later frame's copy in a column of its own, `__dashm<k>`, carrying that frame's format and labels, the spec maps the variable to that column for that frame's graphs, and both renderers read, for each graph, its own frame's column and metadata under the variable's name (D-33-07.f, D-33-07.m). So `date` formatted `%td` in one frame and `%tm` in another, `make` stored as a string in one and a number in another, or `foreign` labelled Domestic/Foreign in one and US/Abroad in another, each draws as twoway draws it in its own frame, with no refusal. Two shapes are still refused at build, with a message naming the graph and the frames: a graph whose frame no longer exists (r(111), Stata's `frame <f> not found`), and a `link()` group joining graphs of different frames (r(198)); so is a `filter()` whose variable two frames abbreviate differently (r(198)) or store as a string in one and a number in the other (r(109), Stata's "type mismatch" code, naming the variable and the two frames; D-33-07.h, DECISIONS A-28). One result changes, so the CHANGELOG line goes under Changed behaviour (PD-7): a graph registered in a frame other than the one `dash build` runs in used to be drawn from the build frame's data, or refused r(111) when its variables were not there; it is now drawn from its own frame, as twoway would have drawn it when the command ran.

**Test order and commit rule.** 33-07-01 writes the regression tests (cscript cases and pytest) red; 33-07-02 records the frame at registration; 33-07-03 the build-time stack, its split columns included; 33-07-04 the renderers' per-graph view of a frame's own columns and metadata (A-23); 33-07-05 help and CHANGELOG; 33-07-06 runs the covering tests and cscripts and commits once: `Draw each registered graph from the frame it was registered in (WP-33 33-07)`.

### Section decisions

- **D-33-07.a (the syntax is twoway's prefix; P4-7).** dash adds no option. A graph's frame is the frame its named registration runs in, so `frame <f>: dash <plot> ..., name(<g>)` -- Stata's prefix, as `frame <f>: twoway ...` -- registers g in f, and the registration's variable checks and refusals are already twoway's own in that frame. `_dash_register_graph` stores `global dash_frm_<g>` = `c(frame)` by value (Mata `st_global("dash_frm_" + name, c("frame"))`) on every registration, overwriting the last; `_dash_item_globals` retires it with the graph's other globals; `_dash_clear` sweeps `dash_frm_*`. Nothing is pending between two commands (no global is set before a registration and read after it), so a refused registration leaves nothing behind. `frame(f)` stays refused exactly as `twoway ..., frame(f)` refuses it (r(198); Q3307-2 compares the two live). The one-line route (no `name()`) is unchanged: it draws at once from the current frame, as twoway does. KPI cards (`dash kpi`, dash's own subcommand) and image panels (33-06) record no frame: a KPI reads the frame current at `dash build`, as today.
- **D-33-07.b (unchanged path).** The build is "single-frame" when every registered graph's `dash_frm_<g>` equals the build's `c(frame)` (a graph with no `dash_frm_<g>`, registered by an older dash in the same session, counts as `c(frame)`); then `_dash_prepare_spec` runs exactly as today (BR-33-07.4): no frame prefix, no frame key, the generators called with no frame argument.
- **D-33-07.c (no frame switch; the stack is temporary).** dash never changes the working frame (`cwf` is not used). A command that must read frame F runs as `frame F: <command>`, held in a local prefix `_fpx` (`frame <F>:`, or empty on the single-frame path) and written `` `_fpx' <command> ``. Measured 20oct2026 in a scratch session (StataNow 19.5, console): under the `frame` prefix `c_local` and `mata: st_local()` set the caller's locals, `_rc` is set after `frame F: capture ...`, a macro-held prefix works, the working frame is restored when the command fails, and a frame made with a `tempname` in a program is dropped when that program ends. So the stack frame is named by `tempname _dash_stk` in `_dash_prepare_spec` (dropped on success or error when the program ends) and read through `frame \`_dash_stk':`.
- **D-33-07.d (every plot and column carries its frame).** In a multi-frame build every plot's qualifier pair of every graph -- the empty pair included -- is entered in the qualifier table with the graph's frame (the build's `c(frame)` for KPIs), so every plot and KPI is selected by a column; a plot with no `if`/`in` gets the column `1` on its frame's rows and `0` elsewhere. The time-series, weight-expression and sort tables are keyed by frame the same way: the same expression or sort list in two frames is two columns, each made in its own frame, so no column ever mixes two frames' meanings.
- **D-33-07.e (what each frame keeps; REVIEW-1 R1-22).** Frame F keeps, in its preserved copy, exactly: the variables of F's graphs that the registry loop gathers for export (each graph's `gvars`, the `qvars` that exist, its hover() names), the base variable of each of F's time-series columns (its format and label give the column's, `_dash_tsop_meta`), each filter variable F holds, and -- for the build frame only -- each KPI's variable and weight; plus the columns F made. A variable F splits (D-33-07.f) is kept under its split column `__dashm<k>`, not under its name. Nothing else of F is copied.
- **D-33-07.f (shared variables keep each frame's metadata; DECISIONS A-23, replacing REVIEW-1 R1-20's refusals).** A variable v in two or more frames' keep lists is compared by its record `kind|format|vlname|vlhash|varlabel` (`_dash_var_meta`, made in each frame before anything is renamed). The first frame in plan order that keeps v (the owner) keeps it as the stack column `v`; a frame whose record matches the owner's adds its rows to that column (its rows are disjoint by D-33-07.d). A later frame F whose record differs from the owner's in storage kind (string or numeric), display format, value-label contents (`vlhash`) or variable label -- `_dash_frames_clash` names the first that differs; a value-label set *name* alone is not a difference -- keeps v under a split column `__dashm<k>` instead: `_dash_frames_one` renames v in F's preserved copy after F's working columns are made (so every qualifier, time-series, sort and weight column F makes from v read F's own v), reusing the `__dashm<k>` an earlier frame made for v with an identical record, else taking the next k (k = 1, 2, ... over the build, in plan order of frames, then F's keep-list order). Each split is recorded in the Mata external asarray `_dash_frames_split` (key `F + char(0) + v`, value the column) and, for each graph of F whose own variables (`_dash_frames_gkeep`, TR-33-07.5) hold v, in the spec map `build_options.frame_cols`: `{"<graph>": {"<v>": {"col": "__dashm<k>", "frame": "<F>"}}}`, written only when a split exists, so no other build's spec changes. **Value-label sets of one name.** `append` never replaces a value-label definition already in memory (Stata's `help append`, option `nolabel`), so when a kept variable or made column of F uses a set named L and an earlier frame's kept variables use a set named L with other contents, F's preserved copy gets `label copy L __dashl<j>` and `label values` of each of F's variables on L moved to `__dashl<j>` (one `__dashl<j>` per distinct pair of L and contents over the build, reused across frames; Mata external asarray `_dash_frames_lsets`, key `L + char(0) + vlhash`). Numeric storage types that differ (int and float) are promoted by `append`, as Stata does, and make no split. Nothing is refused for a shared variable a graph draws: a differing storage kind is split like the rest, so no shape of shared data stops a build except a `filter()` over a variable two frames store as a string and as a number, refused r(109) by D-33-07.h (DECISIONS A-28) -- A-23 leaves a gallery row static only for a dataset missing from the cache (33-08's D-33-08.f), and a refusal here would stop a whole gallery page.
- **D-33-07.g (time-series operators, sort(), weight expressions; P4-4).** Taken in a multi-frame build like any other graph: each expression is rewritten into its column with the graph's frame key (D-33-07.d), each frame makes its own columns in itself -- `L.close` under that frame's `tsset`, a `sort()` rank over that frame's rows, `[aw=pop/1000]` from that frame's `pop` -- and the rewrite of a graph from frame F runs under `frame <F>:`, so each expression is checked against F's variables. A plain weight variable is taken as before.
- **D-33-07.h (links, brush, filters).** A `link()` group (or `link(_all)`) naming graphs of two frames is refused r(198) `link() joins graphs from frames <a> and <b>; a link group draws from one frame`. Brushing acts within link groups, so it follows. Each `filter(v ...)` group is resolved in every frame of the build: its variable is `unab`bed in each frame that holds a match, and every frame that does must give the same full name (else r(198) `filter() variable <v> abbreviates <a> in frame <f1> and <b> in frame <f2>`) and the same storage kind (else r(109), Stata's "type mismatch" code, `filter() variable <v> is a string in frame <f1> and numeric in frame <f2>`, naming the variable and the two frames: one filter control cannot offer both texts and numbers; DECISIONS A-28, documented in the help with the frame prefix, TR-33-07.6); every graph whose frame has no match is added to that group's `exclude()` list before the filter JSON is written, and no other graph is: a graph whose frame holds the filter's variable in a split column `__dashm<k>` (D-33-07.f) is not excluded (DECISIONS A-27; PD-12: a filter applies to the graphs whose frame holds its variable). The filter applies to such a graph through its frame view (D-33-07.m): the graph's sources hold its own frame's values under the variable's name, and the page's filter mask (`dash_filter_mask`, unchanged) tests those values as it tests every other graph's; the widget is built from the filter's rows with, on each split graph's rows, that graph's split column read in place of the stack's `v` (`_dash_filter_frame_column`, TR-33-07.8), so its choices are every target frame's values and the stack's empty `v` on those rows adds no missing choice; its title and value labels are the owner frame's, as for any dashboard-wide reader. A filter variable no frame holds is refused r(111) as today. KPI cards follow filters and selections as today, over the build frame's rows.
- **D-33-07.i (served).** `dash serve` runs `_dash_prepare_spec` too, so it gets the same stack and the same `frame_cols` map; the served app reads the map through the same helpers as the saved page, copied into it (D-33-07.m, R2).
- **D-33-07.j (the registry loop at build).** In a multi-frame build each graph's pass of the registry loop (`_dash_prepare_spec`'s per-graph reading: `_dash_qual_rewrite`, `_dash_wexp_rewrite`, `_dash_tsop_rewrite`, the t-option unit check, the qualifier-variable `confirm`s and `_dash_extract_hover_vars`) runs under `` `_fpx' `` for that graph's frame, so a variable that exists only in its frame passes and one missing there is refused in Stata's words, naming the graph.
- **D-33-07.k (a frame that is gone).** A graph whose recorded frame no longer exists at build (dropped, renamed, or a `tempname` frame whose program ended) is refused r(111): Stata's `frame <f> not found`, then `dash build: graph <g> was registered in frame <f>.`, before anything is written. It is never drawn from another frame.
- **D-33-07.l (CHANGELOG, PD-7).** The changed result of the Overview's last paragraph is one line under `### Changed behaviour (may need your do-files changed)` (TR-33-07.7).
- **D-33-07.m (the renderers' per-graph view; DECISIONS A-23).** Both renderers take the `__dashm<k>` columns `build_options.frame_cols` names as data (passed in `_dash_take_qual_columns`'s `keep`, as the time-series columns are) and read each graph the map names through one view made by `_dash_frame_view`: a copy of the data frame in which each mapped variable v holds its split column's values, and copies of the metadata maps (variable labels, value labels and their set names, display formats, numeric formats, date kinds, storage types, string flags) in which v takes its column's entries. Every per-graph reader runs inside the view -- saved page: the page plan's per-graph pass (`_ensure_embed`), the table text (`_dash_add_table_text`) and source and figure building with by() expansion (`_build_sources_and_figures`), so hover text, marker labels, colour keys, axis titles, value-label ticks and date formats are the graph's own frame's; served app: the same passes in `make_document`; at export, `_dash_stata_tick_requests`, which writes the split column in the graph's Stata tick requests. Every dashboard-wide reader (KPI cards, filter widgets, the CSV download) reads the stack as it is, except that a filter widget reads a split graph's rows through `_dash_filter_frame_column` (D-33-07.h, A-27); the CSV heads a split column `<v> [frame <F>]`. The saved page's JavaScript is unchanged: a figure's sources hold the graph's columns under the variable's name and its formatters carry the graph's formats as arguments, as today (if a JS twin turns out to read a page-wide map keyed by variable name, stop and report: the manifest gives 33-07 no JS). Nothing is printed: the graph draws as twoway draws it in its own frame.

## Risk: [red] -- the build's data path

**Why.** Every dashboard's export runs through `_dash_prepare_spec`; a mistake changes rows drawn. **Risk factors.** The qualifier and working-column table keys; per-frame column generation; the KPI and filter paths; split columns of shared variables and the renderers' per-graph view of them (D-33-07.f, D-33-07.m: a reader left outside the view would draw one frame's graph with another frame's format or labels); a do-file that registers graphs in one frame and builds in another now draws the registration frame (the CHANGELOG says so); R12 (`_dash_prepare_spec` was edited by 33-06 last batch and lost the size-cap accounting in 33-15 -- re-read). **Mitigation.** The single-frame path is byte-identical (pinned by Q3307-5's spec and data digest); every multi-frame behaviour is a cscript case against `frame f:` runs of the same commands; no `cwf`, so the user's frame cannot be left changed (D-33-07.c, measured); impact analysis before each edit; one cscript case per kind of shared-variable difference (storage kind, format, value label with its set name, variable label) reading the exported data and spec, a page test reading each graph's drawn labels and formats, and a mode-parity entry for the view (R8); clear refusals for the shapes a build cannot hold (a gone frame, a cross-frame link group, and a filter over a variable two frames store as a string and as a number, r(109), DECISIONS A-28).

## User stories

- US-33-07.1 As the dashboard author, I want each registered graph to read the frame I registered it in, with every graph feature it would have there, typed as twoway's `frame f:` prefix, so that one dashboard can show graphs of several datasets without a new option to learn.
- US-33-07.2 As the README reader, I want each plot type's gallery page to hold that type's examples, each drawn from its own dataset, in one dash build (P4-1).

## Business requirements

- BR-33-07.1 A graph registered under `frame f:` draws exactly the rows and values `frame f: twoway <same command>` draws, `if`/`in`, time-series operators, `sort()` and weight expressions included, whatever frame `dash build` runs in.
- BR-33-07.2 Graphs of different frames cannot share a link group (r(198)); a filter never empties a graph whose frame lacks its variable, and applies to every graph whose frame holds it, however that frame formats or labels it (A-27).
- BR-33-07.3 A build with a graph whose frame is gone is refused with a message naming the graph and the frame, before anything is written.
- BR-33-07.4 A build whose graphs were all registered in the frame it runs in writes the same spec and data as before, byte for byte.
- BR-33-07.5 The user's working frame and data are unchanged after a build, whether it succeeds or is refused.
- BR-33-07.6 dash takes no `frame()` option: `frame(f)` is refused as twoway refuses it (P4-7).
