# Section 40-01: Only the selected rows are exported

> Part of: WP-40 (Resource limits) · Items: plat:PT-7 · Risk: red · Batch: 40.1 · Depends on: none (33-15, 33-07, 35-08 and 37-01 landed in earlier WPs) · Blocks: 40-02 · Tasks: 4, 1 commit · Case-id prefix: Q4001

## Overview

**What is wrong today.** The audit (package 5, plat:PT-7 with DG-15, audit :195-197; appendix :2280-2285, :3338-3343): "The cell cap counts _N whatever if/in select (the qualifier adds a column), so 'in 1/100' on 3M obs is refused although the page embeds only the selected rows." Measured: `twoway scatter y x if _n<=100` on 3,000,000 observations draws, rc 0 (on 11,000,000, 0.74 s); `dash scatter y x if _n<=100` and `in 1/100` were refused r(134), "would embed 9,000,000 values (3,000,000 observations x 3 variables)", although the saved page held only the 100 selected rows (1,645,141 bytes on 1,000,000 observations, against 47,792,219 for every row; BUGS.md P0.11). The refusal itself is gone before this WP: ruling P4-3 removed the embedded-cell and page-bytes caps in batch 33.1 (section 33-15). What remains of plat:PT-7 is its cause: `_dash_write_data` (dash.ado:7581) exports every observation of every variable the dashboard uses, whatever the qualifiers select, so the data file, Stata's and Python's memory and the export time scale with `_N` (about 6-8 s and 1.4 GB per million rows, plat:PT-14) where twoway's scale with the rows it draws. The help sentence "the {cmd:$dash_max_cells} limit itself counts only what the saved page will actually embed" (dash.sthlp:3013-3016, Appendix B HR-18) was loose and its cap is gone.

**What will be true after.** Ruling M10 / Q45 with P4-3 and A-12: when nothing on the page needs every row -- no `filter()`, `link()`, `brush()`, `csv` or KPI card, and not a served app -- dash evaluates the qualifiers first and exports only the rows some graph draws; every graph draws exactly what it drew before, the saved page holds the same rows it held, and nothing is refused for size (there is no size cap). When something needs every row, today's export is kept. Two rules read beyond the rows a graph draws (the page plan's comment names them, dash_render.py:60394). twoway lpoly's and lpolyci's grid follows `_N`, every row in memory -- `twoway lpoly mpg weight if foreign==1` draws on 50 grid points over the 22 foreign cars (qualified_stat_truth.json) -- and the renderer takes that `_N` from the rows exported (`len(self.dataset)`), so a subset export would draw 22: each graph's JSON therefore carries its `_N` as `"n_obs"` (D-40-01.d), which the grid reads at build and after a served filter move. lowess's `adjust` divides by the mean of y over every observation in memory (lowess.ado's `summ y, mean` with no if; `_lowess_y_all_mean`, dash_render.py:20665-20679, reads it from `self.dataset`), so a lowess layer with `adjust` selects every row and its build keeps today's export (D-40-01.b). The help says which rows are exported (HR-18). It is a size measure: no message, no refusal, no limit.

**Test order and commit rule.** One item, one commit. Task 40-01-01 writes the failing tests and the S01 truth block and saves the failure text, no commit; 40-01-02 adds the Mata selection and `_dash_put_n_obs`; 40-01-03 wires the subset export and `"n_obs"` on both routes and makes the lpoly grid read it; 40-01-04 flips pins, edits the help, closes the item and commits once with the subject ending `(WP-40 plat:PT-7)`.

### Section decisions

- **D-40-01.a "Selected mode".** On the one-line route always (it takes no filter, link, brush, csv or KPI); on `dash build` (saved) when, after the inherited options are filled in, the build has no `filter()`, `link()`, `brush()`, `csv` and the registry holds no KPI card; never on `dash build, server` or `dash serve` (a served app embeds every observation). The KPI, brush() and served cases are kept as full-row cases beside Q45's filter, link() and csv (A-12).
- **D-40-01.b The selected rows** are the union over every graph of the build of the rows the graph draws, the rule `_dash_embed_plan` already applies to the page (dash_render.py:60422-60495): for each plot record whose type is not `scatteri`, `pci`, `pcarrowi` or `function`, the rows with `G & P`, and, when the graph or any of its plots carries a `qual_col_total` (by(, total)), also `Gt & Pt`; `G` is the graph's `qual_col` == 1 (every row when it has none), `P` the plot's `qual_col` == 1 (every row when none), `Gt`/`Pt` the `qual_col_total` twins (the object's own `qual_col` when it has no twin, as `_dash_total_spec`, :60199, swaps them). A graph with no such plot (only literal types) selects the rows `G` (or `G | Gt`) when it has `by()` -- its panels are built from its by() variable's rows (REVIEW R3-7; 37-01's byempty base) -- and none without `by()`. Computed layers (histogram, kdensity, fits) select their rows (their output is computed from them). A `lowess` record whose `adjust` is set selects every row: its mean is every observation's (Overview), so the selection is then all of `_N`, `_sel_cut` is 0 and the build exports as today (the alternative, a build-time mean carried beside `"n_obs"`, would add a second renderer reader for one option; keeping the full export changes no drawing and needs no ruling).
- **D-40-01.c The user's frame is never reduced.** The selection is a `tempvar` byte column made in the frame the export line reads, after every other working column and after the Stata-ticks step, immediately before `_dash_write_data`. On most commands that frame is the user's own: 35-08 makes the working columns in the user's frame whenever it has room (plan `inplace`, D-35-08.b, the usual case), and 33-07 leaves a single-frame build unchanged (D-33-07.b). Only 35-08's plan `frame` (`frame `_dash_xf' { ... _dash_write_data ... }`) and 33-07's stack of several frames (`frame `_dash_stk': _dash_write_data ...`) export from a temporary frame of dash's own. So, when `0 < r(N) < _N`: (1) where the export line reads the user's frame, the selected rows are copied into a new temporary frame -- `tempname _dash_sf`, `frame put <the exact varlist the _dash_write_data line is given> if `_dash_sel', into(`_dash_sf')` -- the line runs as `frame `_dash_sf': _dash_write_data ...`, and `capture frame drop `_dash_sf'` runs on every exit path; `frame put` copies the variables with their labels, value labels and formats, as `keep` keeps them (frame_put.sthlp), which is everything `_dash_write_stata_data` reads and what 35-08's frame branch copies for the export; the user's frame keeps every observation, and the copy, the data file and Python's memory follow the drawn rows; (2) where the line already runs inside 35-08's temporary frame or 33-07's stack, that frame is reduced with `quietly keep if `_dash_sel'`. The selection column is dropped after the export on every path. No `preserve` is used (it would copy every row). When no row is selected (`r(N) == 0`) the export is today's, so the empty-graph drawing (37-01's) cannot change; when every row is (`r(N) == _N`) it is today's too, with no copy.
- **D-40-01.d The graph's `_N` travels with it; nothing else changes.** Each graph's JSON gains one key, `"n_obs"`: `c(N)` of the frame the graph draws from, read before any subset or stack -- on the one-line route the user's frame; on `dash build` the graph's own frame (33-07: the frame it was registered in, read in its registry pass under that frame's `frame <f>:` prefix), so a graph in a stack of several frames still counts its own frame's rows. `GlyphMapper._lpoly_grid_plan` takes `N` from it instead of `len(self.dataset)` (which, after the subset, counts the rows exported, and in a stack every frame's rows): measured, `twoway lpoly mpg weight if foreign==1` draws 50 grid points over 22 cars, so the 22 exported rows must still give 50. The saved refit's `dash_lpoly_grid_n` (dash_render.py:33102) uses it too, through the refit config's `n_dataset`, which `map_lpoly`/`map_lpolyci` fill from `_lpoly_grid_plan`'s `N` (:21195, :21362); the JS function itself is not edited. A spec with no `"n_obs"` (a mapper used on its own, an older spec) keeps today's `len(self.dataset)`. After a filter move the served app redraws a layer through `_dash_redraw_for`'s `_redraw` (dash_render.py:70146, :70187-70205) on the plan's copy of the mapper (`_dash_plan_mapper`, :69583), whose `n_obs` the per-graph reset has left None: `_redraw` therefore sets the mapper's `n_obs` from its graph `g` before it draws and restores it after (TR-40-01.7), so a served move keeps the graph's `_N` as the saved refit's `n_dataset`, fixed at build, does -- in a stack of several frames `len(df)` would count every frame's rows (an lpoly grid of 22 jumping to 50 after a move). So the renderers are edited in that one place only (TR-40-01.7): every other step reads the rows exported, and the page plan selects the same rows from them. No message is added or changed; the served route and every full-mode build export as today (and carry `"n_obs"` too, equal on a single frame to the rows they export).

## Risk: [red] -- what every one-line command and most builds export

**Why.** The export of every one-line command and most builds changes from all rows to the selected ones; row identities, by() panels, data tables, colour cuts and shared ranges are computed from the exported rows.

**Risk factors.** 1. A graph whose drawing reads rows the selection misses would change: a by() graph of literal plots (R3-7), or any renderer step that reads a whole column rather than its layer's rows (colour-variable cuts, by() group lists, shared axis ranges), or the row count itself (lpoly's and lpolyci's grid, `len(self.dataset)`, dash_render.py:21111). 2. `__dash_row__` (the row's rank among the page's rows, WP-29 P0.11) must stay the same rank. 3. Time-series operators and `_n`-based qualifiers must be evaluated on the full data. 4. The export usually reads the user's own frame (35-08's plan `inplace`, a single-frame build); a `keep` there would drop the user's observations.

**Mitigation.** 1. D-40-01.b is the page plan's own rule plus the literal by() case; TestTheSelectionCoversThePlan asserts, for every CORPUS entry with a qualifier, that the rule's rows hold every row `_dash_embed_plan` keeps, and TestTheDrawingIsUnchanged renders each such entry from the full frame and from the subset and compares `_figure_profile`s, with qualified by(), colorvar() and literal by() entries added when CORPUS lacks them; a difference stops the section at task 01 and is reported; the lpoly grid, the one reader of the row count, reads `"n_obs"` instead (D-40-01.d) at build and after a served move, pinned by TestTheLpolyGrid and Q4001-8/9; lowess's `adjust`, the one reader of a whole column beyond the drawn rows, makes its build select every row (D-40-01.b), pinned by Q4001-2 and Q4001-7 and by TestTheDrawingIsUnchanged's `lowess mpg weight if foreign, adjust` entry. 2. The plan ranks the page's rows, which are the same rows in the same order (`frame put` and `keep` keep the order). 3. Every working column is made before the subset (D-40-01.c). 4. D-40-01.c copies the selected rows out of the user's frame with `frame put` and reduces only dash's own temporary frames; task 01 re-reads both export blocks at the base and records each branch's frame; Q4001-4 (data signature, `c(k)`, `c(changed)`) is the guard.

## User stories

- US-40-01.1 As a Stata user with a large dataset, I want `dash scatter y x in 1/100` to export and hold only the 100 rows it draws, so that a subset of big data builds as quickly as twoway draws it.

## Business requirements

- BR-40-01.1 On the one-line form and on a saved `dash build` with no filter, link, brush, csv or KPI card, dash exports only the rows some graph draws; a build with a lowess layer that takes `adjust` exports every row, because that mean reads every observation.

- BR-40-01.4 Nothing is refused or noted for size; the data in memory are unchanged afterwards.
